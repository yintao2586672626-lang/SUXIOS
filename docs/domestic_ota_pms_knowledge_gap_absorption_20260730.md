# 国内 OTA / PMS 知识缺口吸收与冲突修订

## 1. 目的

本次把 2026-07-30 复核的国内公开官方资料，沉淀为宿析OS可以检索、追溯、版本化和显式报缺的知识，不导入当前酒店经营数据，也不产生任何 OTA/PMS 外部写权限。

本次新增三个全局结构化知识单元：

1. `携程订单履约与结算官方语义合同`
2. `订单来了PMS当前版本官方语义合同`
3. `大众点评独立评价规则官方语义合同`

权威落库路径：

- `database/migrations/20260730_z_absorb_domestic_ota_pms_knowledge_gaps.sql`
- `knowledge_units`：主题、生命周期、已知/未知和真值版本
- `knowledge_chunks`：平台、模块、角色、场景、来源和结构化规则
- `knowledge_base`：员工可读镜像

## 3. 已知的已知

### 3.1 携程订单履约

- 未确认/拒单、确认后推翻、预订不存在、客人到店后无法按原单履约是不同状态。
- 客人自主取消、商家诱导取消、商家引导转店/线下交易必须分开记录。
- 发票请求、开具、交付、争议，和赔付、处罚、结算扣款、申诉是不同业务链。
- 当前规则版本给出的申诉窗口为收到处罚通知后的 5 个工作日；个案执行仍以当前通知和当前页面为准。

### 3.2 订单来了 PMS

- 经营日不自动等于自然日，夜审时点和阻断项由产品版本及酒店配置决定。
- 夜审链包括上一营业日订单/账务检查、应入账/结账处理、营业日切换、报表锁定和差错调整。
- 入住类型、退房类型、订单状态、收银项目、支付方式、支付金额必须分别保存。
- 早餐抛账日期可配置；普通住和钟点住可按产品规则转换；换房在特定配置下可能拆成两个关联订单。
- AR、账龄、权限和操作日志属于独立对象，不能由订单金额推断。

### 3.3 大众点评

- 大众点评是独立平台语义，规则中心域名包含 `meituan.com` 不等于平台身份是美团。
- 大众点评评价不得写入美团 HOS、星级或酒店评价字段。
- 商户本人/员工/利益相关方评价、招募或购买虚假好评、利益交换、要求好评截图、代写、模板化和虚构事实的 AIGC 内容均属于治理风险。
- 可以邀请顾客基于真实体验自愿评价，但不得限定星级、内容或关键词，也不得将权益与评价结果绑定。

## 4. 已知的未知

以下内容继续保留为 `known_unknowns`，不得由行业文章、营销页或历史版本补猜：

- 当前酒店、目标日期、目标订单是否存在履约、账务、评价或处罚事实。
- 携程当前账号的订单状态、处罚通知、实际扣款、申诉入口及私有责任判定算法。
- 订单来了目标租户的产品版本、套餐、配置、夜审时间、字段枚举、AR和OTA自动对账规则。
- 大众点评识别阈值、权重、折叠/不计分、推荐/搜索影响和当前账号投诉/申诉权限。
- 任何规则或运营动作对目标酒店订单、ADR、RevPAR、收入和利润的真实因果效果。

## 5. 精确冲突修订

本次不修改历史迁移，也不宽泛删除知识，只通过前向迁移修订以下精确冲突：

| 旧知识 | 修订后 |
| --- | --- |
| 房费收入缺失时用 `paid_amount` | `room_revenue` 缺失即 `not_calculable`，补字段映射；订单GMV、支付、结算和房费不得互换 |
| 携程曝光默认写成通用 `impression_count` | 只在来源明确时使用展示次数；已核验携程数据中心列表曝光使用去重浏览人数语义 |
| 每个门店一个本地 Profile | 同一已授权账号在同一受控设备复用一个 Profile，账号内按已核验门店切换；不同账号不得共享 |
| 携程/美团点评列为标准自动采集优先级 | 标准自动ETL不采点评；仅允许人工明确触发、账号授权、规则复核后的有界采集 |

历史来源和修订原因仍保存在结构化片段中，便于审计。

## 6. 检索合同

### 6.1 平台隔离

结构化片段必须保存 `platforms`：

- 携程：`["ctrip"]`
- 订单来了：`["pms", "dingdandao"]`
- 大众点评：`["dianping"]`

检索器对显式平台标签做硬过滤。员工镜像没有结构化平台列时，按标题、关键词、正文依次识别平台；显式属于另一平台的镜像不能进入当前平台提示词。

### 6.2 公平取样与截断

收益运营知识不再按旧片段顺序静默取前 N 条，而是按最新知识单元公平轮询：

- `eligible_entry_count`：全部合格片段数
- `entry_count`：本次返回数
- `omitted_entry_count`：未返回数
- `truncated`：是否截断
- `selected_unit_count`：实际覆盖的知识单元数

只要有合格片段未返回，状态必须是 `partial`，并返回 `revenue_operations_knowledge_truncated`。

### 6.3 国内公开资料监测

文化和旅游部、国家统计局、中国饭店协会、市场监管总局四个公开来源快照补齐：

- `source_refs`
- `source_manifest`
- `module_id`
- `roles`
- `scenes`
- `reviewed_at`
- `source_version_fingerprint`
- `seed_owner/seed_key/seed_version`

同时创建 `knowledge_base` 员工镜像。快照只确认标题、日期、链接和来源指纹；正文方法、样本和口径尚未逐篇复核。

### 6.4 决策门禁

`KnowledgeDecisionGateService` 在 AI 检索和 SOP 任务草稿创建前统一检查：

1. 单元与片段生命周期必须为 `active`。
2. `scope`、`evidence_level`、`source_refs` 必须完整。
3. `valid_from/valid_until` 必须覆盖本次使用时间；到达 `review_due_at` 后降级为待复核，不静默沿用。
4. 证据等级：
   - `A`：当前或版本化官方规则、官方统计、官方产品帮助；
   - `B`：已验证运行时、源码或集成合同；
   - `C`：经复核的方法、派生合同或参考模板，只能作为参考并要求人工判断；
   - `D`：未验证、冲突、推断或非运行时材料；
   - `U`：尚未评级。
5. `D/U` 默认不能进入 AI 决策提示词；显式 `case_key` 仍可读取案例，但不会变成当前门店事实。
6. `version_conflict` 不选择 30 天或 90 天等任一版本，只作为 `known_unknown` 生成核验要求。
7. 同一 `conflict_key` 出现不同 `claim_value` 时全部暂缓；只有唯一片段显式标记 `resolution_status=resolved/current/authoritative` 才放行。

员工 `knowledge_base` 继续作为阅读镜像；结构化知识表存在时，AI 不再从无证据等级的员工镜像兜底，避免绕过门禁。

## 7. 运行时边界

- OTA事实只用于渠道分析，不自动成为全酒店事实。
- `订单GMV ≠ 支付金额 ≠ 房费收入 ≠ 结算金额 ≠ 应收/核销 ≠ 会计收入`。
- 不保存 Cookie、密码、验证码、原始会话、住客证件、电话或支付标识。
- 规则知识不授权自动取消、改订、开票、申诉、评价生成、PMS写账或平台写入。
- 目标酒店使用前仍需：酒店身份、业务日期、来源身份、产品版本、保存回读和失败状态验证。

## 8. 更新触发器

出现以下任一情况时，创建新版本并将旧版本标为 `stale`，不要覆盖来源历史：

1. 官方页面的版本号、发布日期、生效日期或条款发生变化。
2. 订单来了产品版本改变夜审、抛账、拆单、AR或权限行为。
3. 大众点评或携程当前账号页面出现与公开规则不同的有效期、入口或状态。
4. 宿析OS检索字段、平台标识、表结构或标准ETL政策改变。
5. 聚焦验证发现跨平台污染、静默截断、来源不可追溯或旧冲突重新出现。
