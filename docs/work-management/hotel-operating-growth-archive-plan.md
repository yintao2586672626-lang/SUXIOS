# 宿析OS「酒店经营成长档案」产品计划书

> 状态：产品方案草案，待用户评审，不代表功能已经开发。
> 版本：v0.1
> 日期：2026-08-03

## 一、结论

“酒店经营成长档案”应当是一个按时间沉淀酒店经营事实、老板判断、执行动作和实际结果的独立页面。

它不是普通操作日志，也不是让 AI 评价老板是否正确。它要解决的是：酒店每天做了很多判断和动作，但三个月后很难准确回答“当时为什么这么做、到底执行了什么、结果怎样、哪些做法值得继续、哪些问题反复出现”。

第一版只做一件事：让一家酒店的关键经营过程形成可信、可回查、可补充的时间线，并与现有“今日经营编排”和“运营执行”互相跳转。

## 二、用户价值

### 2.1 老板真正获得什么

- 不再依赖聊天记录、脑内记忆和零散表格回忆经营过程。
- 可以看到自己的判断、系统建议和实际结果，而不是只看系统的事后结论。
- 某个问题再次出现时，可以直接找到上次如何处理、是否有效、当时的数据条件是否相同。
- 新店长或新运营人员能快速理解这家酒店的历史，而不是从零摸索。
- 年底能够形成一份真实的酒店经营年鉴，而不是临时拼报表。

### 2.2 与“今日经营编排”的关系

```text
今日经营编排：今天要处理什么
        ↓
运营执行：实际决定和做了什么
        ↓
经营成长档案：这件事后来发生了什么，留下了什么经验
```

三者分别管理现在、行动和历史，不在首页继续堆叠一套重复卡片。

## 三、产品定位

### 3.1 它记录什么

每条档案记录一个“经营事件”，主要分为七类：

| 类型 | 例子 | 默认来源 |
| --- | --- | --- |
| 经营事实 | 携程流量下降、周末库存压力、差评出现 | 已保存并回读的 OTA/PMS/人工事实 |
| 系统分析 | 收益分析、Agent 诊断、风险提醒 | 宿析分析模块 |
| 老板判断 | “先不降价，观察竞品两天” | 人工记录 |
| 经营决策 | 批准、修改或拒绝某个执行意图 | 审批记录 |
| 执行动作 | 调价、改活动、回复评价、调整库存 | 运营执行及证据 |
| 效果复盘 | 成功、接近成功、失败、仍在观察 | 已保存的复盘记录 |
| 里程碑 | 首次形成完整闭环、连续完成月度复盘 | 人工确认或规则建议后确认 |

### 3.2 它不是什么

- 不是服务器运行日志或员工操作审计页。
- 不是把所有 OTA 原始数据复制一遍。
- 不是 AI 给老板打分或证明 AI 比老板正确。
- 不是只展示好结果的“荣誉墙”；失败和未验证结果同样保留。
- 不是自动修改 OTA、自动发消息或自动生成对外宣传材料的入口。

## 四、核心页面设计

页面名称建议使用“经营成长档案”，导航归入“运营管理”。

### 4.1 页面结构

```text
┌──────────────────────────────────────────────────────────┐
│ 经营成长档案                                             │
│ 酒店：敦煌漠蓝新  时间：近90天  范围：全部  [记录一件事] │
├──────────────────────────────────────────────────────────┤
│ 成长概览                                                 │
│ 有效档案状态｜已完成复盘｜仍在观察｜反复出现的问题       │
├──────────────────────────────────────────────────────────┤
│ 筛选：事实 分析 判断 决策 执行 复盘 里程碑               │
├──────────────────────────────────────────────────────────┤
│ 08-03  周末价格调整复盘                       [接近成功] │
│         当时事实｜老板判断｜执行动作｜实际结果            │
│         携程 · 2026-08-01 · 已核验 · 证据 3 条            │
│         [查看来源] [补充批注] [加入里程碑]                │
│                                                          │
│ 08-01  首次完成同店同日 OTA 事实回读          [里程碑]   │
│                                                          │
│ 07-29  流量下降但暂不降价                     [观察中]   │
└──────────────────────────────────────────────────────────┘
```

### 4.2 顶部“成长概览”

第一版不做虚假的成长分数，也不统计“没有证据”等于“0”。只显示当前确实能从档案回读得到的状态：

- 已形成档案的经营事件数量。
- 已完成效果复盘的事件数量。
- 仍在观察、等待结果的事件数量。
- 被系统识别为重复出现、但尚未解决的问题数量。

任何一项数据无法读取时显示“未取得”或“读取失败”，不显示 0。

### 4.3 时间线卡片

每张卡片固定回答六个问题：

1. 发生了什么？
2. 当时掌握了哪些事实？
3. 老板或负责人怎么判断？
4. 最后做了什么？
5. 实际结果是什么？
6. 证据在哪里？

卡片必须同时显示：酒店、业务日期、平台/数据范围、来源模块、可信状态和证据数量。点击“查看来源”必须回到对应事实、诊断、任务、审批或复盘记录。

### 4.4 “记录一件事”

允许老板或运营人员补录系统里没有的经营背景，例如装修、当地活动、临时停房、人员变动、老板个人判断。

最小字段：

- 酒店（必须明确选择，不允许默认串店）。
- 发生日期和时间。
- 事件类型。
- 标题。
- 实际发生的事情。
- 当时的判断或处理方式（可空，不能自动补写）。
- 数据范围：携程、美团、PMS、全酒店、人工背景或其他。
- 证据附件/链接（可空；为空时标记“人工记录、未核验”）。

保存后必须用返回的记录 ID 再读取一次，酒店、日期、类型和内容一致后才显示“保存成功”。

### 4.5 老板批注

老板可以在系统分析或复盘卡片下补一句自己的判断，例如：

- “系统建议降价，我决定先观察，因为当天有本地会议。”
- “结果变好，但不能证明一定是调价造成的。”
- “下次遇到同类情况先查房型库存，不直接改活动。”

批注是独立思考的保留，不覆盖原始分析，不修改历史事实；新增批注形成新版本并保留上一版。

## 五、数据来源与可信边界

### 5.1 第一版可直接复用的现有数据

宿析当前已经具备：

- “今日经营编排”的酒店、日期、任务和状态入口。
- 运营执行意图、审批、执行证据和效果复盘。
- `hotel_operating_memories` 经营记忆索引。
- 从已执行且已完成复盘的任务沉淀经营记忆，并进行严格保存/回读校验。
- 经营记忆的事实、分析、决策、执行复盘和 SOP 分层，以及已核验、部分核验、未核验、冲突和失效状态。

因此第一版不新建第二套“执行记忆”数据结构，而是在现有经营记忆之上补齐独立页面、人工经营事件、老板批注、里程碑和时间线聚合。

### 5.2 必须保持的边界

- 每条记录绑定 `tenant_id`、`hotel_id` 和发生日期；跨酒店读取直接拒绝。
- 携程/美团事实只代表对应 OTA 渠道，不自动写成全酒店结论。
- PMS 或线下数据没有取得时明确显示缺失，不拿 OTA 数据代替。
- 人工补录默认是“人工记录、未核验”，除非后来关联到可信来源。
- “执行后指标上涨”只能写成前后变化，不能自动宣称是该动作造成。
- AI 摘要只整理已有记录，不能补造不存在的判断、结果或证据。
- 本模块不写 OTA、不外发消息、不自动批准任务。

## 六、P0 最小可用版本

### 6.1 功能范围

1. 新增“经营成长档案”独立页面和导航入口。
2. 按单酒店、日期范围回读已有经营记忆，生成时间线。
3. 支持按事实、分析、判断、决策、执行、复盘、里程碑筛选。
4. 从档案卡片跳转到对应来源记录。
5. 支持手工记录经营事件，保存后严格回读。
6. 支持给档案增加老板批注，原记录不可被覆盖。
7. 支持把一条记录人工设为里程碑，并保留操作者和时间。
8. 从“今日经营编排”已完成或待复盘事项进入对应档案上下文。
9. 提供加载中、暂无数据、部分数据、读取失败、迁移未完成和无权限状态。

### 6.2 暂不进入 P0

- AI 自动生成酒店成功故事。
- 酒店之间的排名和成长分数。
- 自动判断老板决策正确率。
- 自动把单次成功提升为 SOP。
- 自动导出年报、对外海报或公众号内容。
- 使用未经核验的 PMS、竞品、天气、活动或线下经营数据。

## 七、P0 用户路径

### 路径 A：回看一次经营动作

1. 老板进入“经营成长档案”。
2. 选择酒店和近 90 天。
3. 点开“周末价格调整复盘”。
4. 查看当时事实、判断、执行动作和结果。
5. 点击来源，进入对应运营执行记录核对证据。
6. 返回档案并补充自己的批注。

### 路径 B：记录系统没有的背景

1. 点击“记录一件事”。
2. 选择酒店、日期和“人工背景”。
3. 记录“当地大型活动临时取消，决定不立即降价”。
4. 保存。
5. 系统严格回读成功后，时间线出现“人工记录、未核验”卡片。

### 路径 C：从今天进入历史

1. 在“今日经营编排”完成一项任务并保存复盘。
2. 点击“沉淀经营记忆”。
3. 保存并严格回读成功。
4. 首页状态更新，同时在成长档案出现对应事件。

## 八、验收标准

### 8.1 核心闭环

- 用户可以从导航找到“经营成长档案”。
- 精确显示当前酒店、业务日期、平台/数据范围、来源和质量状态。
- 已沉淀的运营复盘能够出现在对应酒店的时间线中。
- 人工事件能够保存、按记录 ID 回读，并在页面真实显示。
- 老板批注不会覆盖原始分析或历史版本。
- 点击“查看来源”能进入正确事实或任务，不只弹出摘要。
- 今日经营编排完成状态与成长档案沉淀状态一致。

### 8.2 失败与缺失

- 无记录显示“暂无档案”，不显示“经营稳定”或全为 0 的统计卡。
- 读取失败显示真实失败，不沿用上次缓存冒充本次成功。
- 酒店身份不一致时拒绝展示或保存。
- 缺少来源、日期或证据时显示未核验/部分核验，不升级为可信经营结论。
- 手工补录未附证据时仍可保存，但必须明确标记人工和未核验。
- 数据库迁移未完成时显示功能未启用，不显示空白成功页。

## 九、实现建议

### 9.1 最小改动原则

- 复用现有 `hotel_operating_memories`，不复制原始 OTA 数值。
- 复用现有经营记忆列表、单条回读和从执行任务沉淀记忆的接口。
- 增加时间线聚合读取、人工事件保存、批注和里程碑所需的最少接口。
- 新页面保持宿析现有视觉体系；时间线是核心，图表不是 P0 必需项。
- 所有写入先保存，再按 ID 严格回读，然后刷新时间线。

### 9.2 建议的页面组成

- 页面头：酒店、日期范围、事件类型筛选。
- 成长概览：只显示有证据可算的状态数字。
- 主时间线：统一呈现事实、判断、执行和结果。
- 事件详情抽屉：完整证据、来源和版本记录。
- 新增事件弹窗：人工经营事件录入。
- 老板批注区：追加判断，不修改原文。

## 十、后续阶段

### P1：经营月鉴

从一个自然月的可信档案生成可编辑“经营月鉴”：本月关键变化、重要判断、已执行动作、成功/失败/观察中事件、反复问题和下月需要继续观察的事项。生成内容必须逐条链接原始档案；没有证据的章节保持空缺。

### P2：经验复用

当同一酒店在不同日期出现多次相同问题，系统可以提示“查看过去相似事件”。只有多次独立执行、复盘和结果证据成立后，才允许进入 SOP 候选；不得从一次成功直接生成标准答案。

### P3：多店成长视图

在同租户且用户有权限的前提下，按同一平台、指标口径和日期范围比较各酒店的闭环能力与重复问题。只比较可比事实，不做无口径的总分排名。

## 十一、开发顺序与停止条件

推荐先只完成 P0，不同时开发月鉴和多店视图：

1. 时间线读取现有经营记忆。
2. 打通人工事件保存与严格回读。
3. 打通老板批注和历史版本。
4. 打通里程碑与来源跳转。
5. 与今日经营编排同步状态。
6. 完成一条成功样例和一条缺失/失败样例的页面验收。

当一家指定酒店能够完成“找到页面 → 查看真实历史 → 新增事件 → 保存 → 严格回读 → 页面显示 → 跳回来源”，并且无数据、失败和跨酒店状态均真实时，P0 即停止，不自动扩展到 P1。

## 十二、需要用户评审的产品判断

本草案已经固定技术和数据边界。当前只需要判断产品气质是否符合预期：

> 这个页面的核心是“酒店的经营历史和老板自己的判断”，而不是“AI 对老板的评分”。

如果这个方向成立，下一步再进入 P0 页面原型和真实功能开发。
