# 美团酒店评价与经营规则官方语义合同

## 结论

本知识包把美团公开规则中心、酒店商家规则、酒店管理系统官网和旧直连 FAQ 转成可检索的版本化语义合同。它只解释美团 OTA 渠道与公开 PMS 产品能力，不包含当前酒店数据，也不授权宿析OS自动写价格、库存、订单、点评、申诉或商家资料。

本轮已完成四类纠错：

1. 美团评价与大众点评评价必须拆开。2025 年美团评价总则明确排除大众点评，不能继续使用“美团点评系”作为同一个评分或投诉合同。
2. 美团星级和评分是动态加权指标，不是简单平均分。可确认的候选因素包括评价用户专业度、评价质量、评价时间、诚信度和评价数量，但精确权重、酒店品类算法和排名影响仍未知。
3. 历史资料中的“礼物激励点评”“半年内均可申诉”“HOS 满分 5 分、近 28 天”“拒单量/创建订单量”不再作为现行通用事实。
4. 旧直连 FAQ 同页同时写“最多 180 间夜”和“最多 29 间夜”，并带有未来月份描述和 `©2016` 页脚。该页只保留为历史概念与冲突样本，所有限额、权限、频率和接口行为均须由当前 API、合同或登录后帮助重新确认。

## 已知的已知

### 1. 评价范围与平台拆分

- 美团评价总则适用于美团 App、PC 和小程序的到店体验类评价，明确不适用于大众点评 App、PC 和小程序。
- `platform=meituan` 与 `platform=dianping` 必须分别存储、检索、评分和申诉；不得使用 `meituan_dianping_combined` 作为默认业务口径。
- 美团规则发生冲突时，按其规则文本采用时间上最新发布内容；相同发布时间按评价总则处理。宿析OS仍须保存来源 URL、版本和复核日期。

### 2. 美团星级与评分

- 商户星级和评分是动态指标，由系统综合计算。
- 当前公开候选因素包括评价用户专业度、评价质量、评价时间、诚信度和评价数量。
- 星级计算以商户下全量打星评价为基础，并剔除作弊数据。
- 平台可以调整评价开放或计算逻辑，因此任何固定权重、固定周期、简单平均或确定排名影响都属于未证实推断。

建议语义键：

| 语义键 | 含义 | 决策边界 |
| --- | --- | --- |
| `meituan_review_star_display_value` | 当前后台或页面展示的美团商户星级原值 | 必须带门店、抓取时间、来源页面和原始分制 |
| `meituan_review_score_display_value` | 当前后台或页面展示的评分原值 | 不反推算法，不与大众点评分合并 |
| `meituan_review_weight_model` | 平台评价加权模型 | 固定为 `unknown_private_algorithm`，除非新官方来源披露 |
| `meituan_review_integrity_filter_status` | 评价是否因违规被不展示、折叠或排除计分 | 只保存平台返回状态，不由宿析OS自行裁定 |

### 3. 评价真实性与合规

以下行为不能作为宿析OS的运营建议：

- 商户、亲友、员工、商业伙伴或利益相关方为商户写评。
- 现金、免费餐食、礼品、折扣、抽奖、佣金等利益换评。
- 商户代替用户写评、修改星级、操作用户设备或查验用户写评结果。
- 以模板、图片或固定文案诱导用户按指定内容写评。
- 在用户未体验或未完成体验前索要评价。
- 利用生成式 AI 生产或虚构违背真实性、客观性、公正性的评价文字或图片。

平台可视情形对相关评价采取不予展示、折叠展示或不纳入星级计算等措施。宿析OS可以辅助整理真实服务事实、回复草稿和申诉证据，但不得生成虚假住客体验、自动代写用户评价或组织换评。

### 4. 酒店违规评价投诉

官方指引列出八类典型场景：

1. 同行恶意差评。
2. 门店员工差评。
3. 利用差评威胁勒索。
4. 无理诉求未满足后差评。
5. 辱骂、人身攻击或其他违法违规言论。
6. 泄露隐私。
7. 评错店铺。
8. 内容与事实明显不符。

酒店商家入口：

- APP：美团酒店商家端 APP → 选择门店 → 我的评价 → 对应评价 → 投诉。
- PC：评价管理 → 选择门店 → 对应评价 → 头像下方“举报” → 按提示举证。

执行合同：

- 每条评价限申诉 1 次。
- 官方页面声明申诉处理时效为 3 个工作日内；这是处理时效，不是成功承诺。
- 用户的主观体验描述原则上不能仅因商家不认可而删除。
- 申诉材料必须真实、完整、与评价用户及事件相关；不得伪造、遮蔽关键身份链或复用其他酒店材料。
- 宿析OS只生成证据清单与人工提交草稿，不自动点击提交。

### 5. 酒店信息、交易与履约诚信

美团酒店诚信细则要求线上信息和实际履约一致，至少包括：

- 门店、名称、地址、星级档次、图片。
- 房型是否真实存在，房间面积、床型、窗、独卫、楼层、人数、景观与设施。
- 停车场、泳池、温泉等设施。
- 接送机、接站、早餐、入住离店、外宾、儿童、宠物等服务与政策。
- 不制造虚假订单、销量、评分、评论或补贴。
- 不以早餐、会员、升房等利益诱导美团用户退订并转到线下或第三方渠道。
- 用户未实际到店时不得提前确认入住。

这些规则可用于资料一致性检查和运营风险预警，但不能证明当前酒店已经违规。必须有门店、订单、页面或平台通知的当前证据。

### 6. 服务类规则的版本化口径

2023-04-10 生效的服务细则定义：

- `拒单`：订单提交后、美团尚未确认预订成功前，商家拒绝确认、诱导取消或超时不确认。
- `推翻`：商家确认预订成功后又推翻预订、诱导取消或不按订单提供设施与服务。
- `拒开发票`：未按法律、规则或约定开具符合要求的发票。
- 当版 `拒单率 = 拒单订单量 / 支付订单量`。
- 当版 `推翻率 = 推翻订单量 / 支付订单量`。

这两个公式必须存为 `rule_version=2023-04-10`。当前公式、统计窗口、节假日处理、阈值和处罚在没有当前规则或后台说明时统一为 `unknown`。历史知识中的通用 `rejected_orders / created_orders` 已被撤销，不能继续标为美团官方口径。

### 7. 经营类规则的版本化口径

2023-04-10 生效的经营细则确认：

- 未经用户同意额外收取与预订无关的费用属于经营风险。
- 美团价格明显高于同类房型市场平均价格、其他渠道或自身历史同条件最高成交价，可被归入价格异常。
- 酒店前台同房型报价或促销价低于美团价格属于该版规则描述的前台倒挂场景。

公开规则没有给出“明显”“大幅度”的统一数值容忍区间。宿析OS不得写死价差阈值，也不得据此自动降价；只能提示人工核对同房型、同权益、同取消政策、同税费和同时间条件。

### 8. 美团酒店管理系统公开能力

当前官网公开描述包括：

- PMS 前台、客房、财务、餐饮、资产和日审等模块。
- 美团、飞猪等渠道的订单、房态、房价和门店管理。
- 集团房价、渠道、佣金、权限、现付账、应收账和结算状态管理。
- 收益早报、同行动态、RMS、智能定价和经营数据展示。
- 门锁、客控等开放平台集成。

这些只能标为 `product_capability_claim`。以下均仍未知：

- 当前租户实际购买并启用的模块。
- 字段定义、业务日、税费、夜审时点、刷新延迟和回补机制。
- 渠道同步成功率、订单遗漏率、对账准确率和权限范围。
- 同行业范围、算法、样本量、HOS/排名关系。
- 使用产品对收入、利润或效率的真实因果增量。

## 宿析OS使用边界

允许：

- 解释美团评价、投诉、信息真实性、履约和价格风险。
- 为人工复核生成事实清单、证据清单和版本提示。
- 将当前账户展示值按门店、日期、来源和质量状态保存。
- 将 2023 规则作为带生效日期的历史规则比较，不把它写成永续阈值。

需要当前数据后才能做：

- 判断某酒店评分、投诉、拒单、推翻、价格异常或经营表现。
- 比较门店、竞对、日期或渠道。
- 计算转化、收入、利润、HOS、排名或投放回报。
- 评价 HMS 同步、对账、收益或效率结果。

禁止：

- 把美团 OTA 数据扩大成全酒店经营事实。
- 自动写价、库存、房态、订单状态、点评、评价回复、申诉或商家资料。
- 组织利益换评、代写用户评价、伪造申诉证据或反推平台私有算法。
- 用旧 FAQ、营销文案或历史文章覆盖当前账户/接口证据。
