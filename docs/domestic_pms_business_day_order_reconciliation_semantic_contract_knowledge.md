# 国内 PMS 经营日、订单状态与对账官方语义合同

## 结论

本知识包把国内公开 PMS 帮助中心、政府统计口径、会计准则和住宿登记规则转成可检索的语义合同。核心纠偏是：

> 预订订单金额、夜审过房费、实收、应收、平台账单、核销/结算和会计收入是不同事实，任何一个都不能在缺少来源映射时替代另一个。

它只提供通用方法和带厂商、版本、地区限定的规则，不包含当前酒店数据，不读取住客个人信息，也不授权宿析OS写订单、房态、账务、支付或公安住宿登记系统。

## 已知的已知

### 1. 订单生命周期必须拆分

建议的标准状态至少包括：

| 标准状态 | 含义 | 不得混同 |
| --- | --- | --- |
| `reserved` | 已建立预订，是否最终确认取决于来源合同 | 已入住、已收款 |
| `confirmed` | 平台或酒店已确认履约 | 实际到店、会计收入 |
| `cancelled` | 预订已取消 | No Show、退款完成 |
| `no_show` | 应到未到并按当前 PMS 流程处理 | 主动取消、在住 |
| `checked_in` | 已办理入住 | 预订确认、已退房 |
| `in_house` | 当前在住 | 已退房、已结算 |
| `checked_out` | 已办理退房 | 已平账、已收款、已核销 |
| `unmapped_source_status` | 来源状态尚未映射 | 不得用默认状态猜测 |

每条状态事实至少保存：

`system_hotel_id`、来源系统、来源门店 ID、来源订单 ID 或脱敏关联键、原始状态、标准状态、状态发生时间、营业日、抓取/同步时间、映射版本和质量状态。

“预订人、联系人、付款人、实际入住人”也必须分开。住客个人信息只在获得授权且业务必要时处理，知识库不保存姓名、证件号、手机号、支付账号或原始订单明细。

### 2. 金额和财务状态必须拆分

| 语义键 | 含义 | 不能自动替代 |
| --- | --- | --- |
| `booking_order_amount` | 预订或订单在当前来源展示的订单金额 | 过房费、到账、会计收入 |
| `room_charge_posted_amount` | PMS 已入账/过账的住宿房费 | 收款、平台结算 |
| `payment_collected_amount` | 已收取或支付通道确认的款项 | 已履约收入、应收核销 |
| `accounts_receivable_amount` | 应收账余额或发生额 | 现金、已核销收入 |
| `external_statement_amount` | OTA、银行或支付机构账单金额 | PMS 账面真值 |
| `settlement_writeoff_amount` | 经核对后已结算或核销的金额 | 原订单金额、会计确认时点 |
| `accounting_revenue_amount` | 按适用会计政策确认的收入 | 预收、押金、代收或可退还款 |
| `refund_amount` | 已发生或已确认的退款 | 订单取消金额 |
| `reversal_amount` | 对错误账项的冲账/反向记录 | 静默覆盖原交易 |

财政部收入准则说明：收到钱不必然等于已确认收入；可退还款项、代收款项或尚未完成履约义务的对价可能仍是负债。PMS 夜审过房费也不自动等于银行到账或 OTA 已结算。

### 3. 经营日和夜审

西软 XMS 的版本化帮助显示，夜审用于：

- 对当前营业日进行汇总和检查。
- 在通过预审后为在住房间过当晚房费。
- 更新系统数据并生成营业日报、房费入账表、试算平衡表等。
- 在该版本流程中，红色检查项和退房未平账列表可阻断夜审。

宿析OS因此必须分别保存：

- `calendar_date`：自然日。
- `business_date`：PMS 营业日。
- `captured_at`：采集时间。
- `night_audit_status`：未开始、预审、阻断、过房费、更新完成或来源原值。
- `night_audit_completed_at`：可核验时保存完成时间。

夜审切日时间、过账策略、未平账阻断项、自动过房费范围和跨午夜归属必须从目标酒店当前 PMS 配置确认，不能写死为 00:00、凌晨 2 点或任何通用时间。

### 4. OCC、ADR 与 RevPAR 的转移边界

北京市公开统计页可确认：

- `平均房价 = 客房收入 / 实际出租间夜`
- `平均出租率 = 实际出租间夜 / 可出租房间天数 × 100%`

宿析OS只有在同酒店、同营业日/期间、同住宿范围、同税费口径且分子分母完整时，才可以进一步计算：

- `ADR = aligned_room_revenue / actual_rented_room_nights`
- `OCC = actual_rented_room_nights / available_room_nights × 100%`
- `RevPAR = aligned_room_revenue / available_room_nights`

每次计算必须明确：

- 客房收入是含税、未税、服务费前后、毛额还是净额。
- 订单取消、No Show、日租/钟点房、免费房、自用房如何处理。
- 维修房、停用房、锁房和临时增减库存是否进入可出租分母。
- 实际出租间夜取入住、过房费、离店还是统计报表口径。
- 经营日是否已夜审完成，数据是否仍会回补或冲账。

缺任何关键分子、分母或范围时返回 `null`/`not_calculable` 和缺口，不得补零或借用 OTA 渠道数据。

### 5. 客房收入与全酒店收入分开

北京市经营情况统计将客房、餐饮、商品和其他收入分列，并注明其统计营业收入为不含增值税口径。由此形成两个保护边界：

1. 客房 PMS 的住宿房费不能自动写成全酒店总收入。
2. 即使都是“收入”，含税/未税、毛额/净额、营业收入/会计收入也必须分别标记。

### 6. OTA 预付、佣金和支付对账是三条链

#### OTA 预付/AR 对账

西软 2023 帮助描述的流程是：导入 OTA 预付账单，和 PMS AR 账逐笔比较，正确后再核销。可抽象为：

- `external_only`：平台账单有，PMS 未找到对应已入账订单。
- `pms_only`：PMS 有应收，平台账单没有对应项。
- `amount_mismatch`：订单已找到但金额不同。
- `matched_unwritten`：已匹配，尚未核销。
- `partial_writeoff`：已部分核销。
- `written_off`：已核销。
- `manual_reviewed`：人工复核完成，仍须保留复核人、时间和原因。

帮助中的“平台每七日提供账单”只属于该示例，不能写成所有 OTA 的固定周期。

#### 佣金对账

佣金必须至少对齐：渠道订单、实际房价/适用金额、佣金规则、计佣基数、税费和取消/退款状态。比例、固定额、底价、净房价等规则不能混用。

界面白/黄/红颜色不能成为数据语义；应保存 `matched`、`amount_mismatch`、`external_only`、`pms_only`、`manual_review_required` 等稳定状态。

#### 支付/银行对账

西软 2025 帮助中的 T+2 自动对账只属于该产品和通道功能。宿析OS需保存：

- PMS 收款流水和外部支付/银行流水的独立身份。
- `matched`、`pms_only`、`external_only`、`amount_mismatch`、`date_mismatch`、`history_incomplete`。
- 人工审核、撤销审核、导入、作废和日期更正的操作痕迹。

“对账成功”只说明两边记录按当前规则匹配，不等于会计收入已经确认，也不等于 OTA 佣金、退款和结算全部完成。

### 7. 错误账项要保留冲账链

公开 XMS 帮助表明，错误费用应先冲账，再按正确方式重新入账，并保留原交易。宿析OS不得直接覆盖原金额，至少应保存：

- 原交易 ID 或脱敏关联键。
- 冲账交易 ID。
- 重入账交易 ID。
- 原因、操作者、操作时间、营业日和来源版本。

## 宿析OS使用边界

允许：

- 解释 PMS 经营日、订单、房费、收款、应收和对账之间的关系。
- 建立跨 PMS 的标准状态，但保留原始状态和映射版本。
- 检查指标分子、分母、营业日、税费和来源是否对齐。
- 生成待人工核对的差异清单和证据要求。

需要当前授权数据后才能做：

- 判断某酒店某营业日的订单、入住、夜审、收入、收款、应收和结算状态。
- 计算全酒店 OCC、ADR、RevPAR 或收入。
- 判断 OTA、佣金或支付对账差异。
- 评价某 PMS 的数据质量、同步成功率或经营效果。

禁止：

- 把 OTA 渠道数据替代 PMS 全酒店事实。
- 把订单金额、到账或夜审过房费直接写成会计收入。
- 保存住客姓名、证件号、手机号、支付账号或未脱敏订单明细到知识库。
- 自动修改订单、房态、账项、支付、核销、夜审或住宿登记系统。
- 把厂商示例周期、地方时限或政府汇总统计外推为所有酒店规则。
