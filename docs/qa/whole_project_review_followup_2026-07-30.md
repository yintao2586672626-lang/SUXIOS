## 1. 结论

本轮没有发现新的、仍未处理的已证实 P0。已证实并完成最小修复的主要问题有三项：

1. 普通账号进入页面时仍会自动请求 Revenue AI 高权限接口，形成不必要的 401/403、错误噪音与状态污染。
2. 携程、美团组合指标在一侧缺失时会丢弃另一侧已知值，用户无法分辨“全缺失”和“已知部分合计”。
3. 当前酒店没有完成唯一 PMS 绑定时，“实时同步”按钮仍可操作，用户会触发一个必然失败的路径。

同时，当前共享工作区中其他功能任务修复了通知页重新挂载、发送记录重试语义、全局当前酒店联动等问题。本报告只把这些作为当前快照事实，不把其他任务的贡献归入本轮直接修改。

在规则与架构层面，没有证据支持当前进行全量重构。最主要的风险仍是：

- 主前端脚本和模板体积大、多人共享写入时构建容易漂移。
- 本地环境使用 `development_fallback`，缓存与锁为 `not_enforced`；本地可用不等于生产多实例安全。
- 真实 OTA 目标日、同店同日三源、生产定时器、真实企业微信回执、部署与 CI 仍必须与代码/测试证明分层。

## 3. 发现与修复

### F-01 — P1 — 普通账号自动请求 Revenue AI

#### 已证实根因

页面初始化会调用 Revenue AI overview；调用前没有与后端能力一致的前端权限门禁。普通账号因此也会发起高权限请求。

#### 影响

- 产生可避免的 401/403 与错误日志。
- 页面初始化状态可能被无权限接口失败污染。
- 高权限能力的展示与实际授权边界不一致，增加后续误用风险。

#### 最小修复

- 增加统一 `canUseRevenueAi()`，只接受超级管理员或显式 `can_use_ai_decision`、`ai.view`、`ai.execute` 权限。
- `loadRevenueAiOverview()` 在发起网络请求前直接返回，不用“请求失败后隐藏”代替权限控制。
- 增加负向回归，验证普通账号不会触发网络调用。

#### 状态

已修复；目标 Node 回归通过。

### F-02 — P1 — 双 OTA 部分事实被误表达

#### 已证实根因

组合指标只有在携程与美团两侧都返回时才计算合计；任一平台缺失时，已知平台的值也被丢弃，并统一表现为未返回。

#### 影响

- 把“携程已知、美团缺失”错误压扁成“完全未知”。
- 用户无法使用已验证的部分事实，也看不到缺口属于哪个平台。
- 下游文案可能把部分数据误当完整合计，或反过来隐藏已知事实。

#### 最小修复

- 对已知平台值求部分小计。
- 缺少任一平台时设置 `dataStatus: partial`。
- 明确显示 `合计不完整` 与缺失平台，不以 `0` 填充缺口。
- 两侧都缺失时保持 missing；两侧齐全时才标记完整。

#### 状态

已修复；新增运行时函数夹具覆盖完整、部分、全缺失三种情况。

### F-03 — P1 — 未绑定 PMS 时仍可点击实时同步

#### 已证实根因

实时同步按钮只受加载状态约束，没有要求当前酒店 `binding_status === 'configured'`。

#### 影响

- 用户进入一个注定失败的操作路径。
- 失败看起来像系统或网络故障，实际是配置前置条件未满足。
- 多酒店场景中容易把“当前酒店未绑定”误判成 PMS 服务不可用。

#### 最小修复

- 唯一 PMS 绑定未配置时禁用实时同步。
- 按钮 title 明确提示“请先为当前门店配置唯一 PMS”。
- 保留酒店级绑定状态，不使用其他酒店的配置兜底。

#### 状态

已修复；PMS 目标回归通过。

### F-04 — P2 — 合法 UI 迁移后测试守卫仍匹配旧结构

#### 已证实根因

六处 Node 合同测试仍依赖旧文案、旧 Tailwind 类、旧 DOM 结构或旧酒店入口：

- 运营自动化中心仍要求旧的“选择通知群”文案。
- 携程当前酒店 UI 仍按旧的单行 DOM 匹配。
- PMS 使用记录只允许旧独立页面。
- AI 工作台未考虑三源驾驶舱模式的隐藏门禁。
- 美团 PMS 测试硬编码旧按钮颜色。
- 美团空状态仍要求旧文案。

#### 影响

- 真实功能正确但完整 Node 套件产生假失败。
- 团队可能为“让测试变绿”回退已经完成的真实 UI 迁移。
- 发布守卫失去区分功能回归与合同陈旧的能力。

#### 最小修复

只更新合同到当前真实语义，不降低安全、酒店隔离、数据真实性或操作门禁：

- 断言每酒店唯一 Webhook 推送通道。
- 容忍当前 span 布局但继续验证当前酒店约束。
- 允许完整 PMS 页面或驾驶舱 PMS 模式记录使用。
- 明确三源驾驶舱下隐藏独立 AI 数据卡。
- 使用语义类名校验按钮。
- 校验当前真实空状态文案。

#### 状态

已修复；六个原失败测试的目标重跑均通过。

## 4. 稳定性、规则与架构结论

### 4.1 启动与健康

本轮复核时：

- `GET /api/health` 返回 HTTP 200。
- application、database、database schema、competitor report idempotency 为 `ok`。
- local state 为 `development_fallback`。
- cache 与 lock 为 `not_enforced`。

结论：本地开发栈可用；这不是生产缓存、分布式锁、单实例、定时器或持久状态的证明。

### 4.2 资源与构建

共享前端在并行任务持续写入时多次触发源/产物漂移保护。该保护避免把不同时刻的源码、模板与压缩产物混为一版，属于正确失败。

已观察到的风险放大器：

- `public/app-main.js` 与合并模板仍是高耦合热点。
- 构建需要统一所有 fragment、渲染产物、入口 hash 和 Tailwind 产物。
- 启动 gzip 已进入警告区间，但尚未越过硬限制。

当前不进行大文件拆分重构：没有证据证明它是本轮功能故障根因，而且脏工作区中大规模重构会显著增加覆盖和回归风险。

### 4.3 数据真实性

本轮继续坚持：

- 缺失不转换成 `0`。
- 单平台已知值可以显示，但必须标记 `partial`，不能称为完整双平台合计。
- OTA 事实只支持渠道分析，不上升为全酒店收入、入住率或利润。
- PMS、订单、夜审房费、实收、应收、核销、会计收入是不同阶段，不能相互替代。
- AI 只接收授权范围内、带来源/酒店/日期/质量状态的输入；无权用户不发起 AI 请求。

### 4.4 规则与守卫

当前规则方向一致：

- `AGENTS.md` 与协作章程均要求功能优先、真实状态、酒店隔离和最小改动。
- `rules/` 负责权限与边界，`hooks/`/package scripts 负责可执行守卫。
- 守卫应随真实结构演进；更新陈旧合同，不删除规则历史、不放宽事实边界。
- “测试通过”只能证明当前代码合同，不替代外部账号、真实采集、保存回读、真实送达或部署证明。

### 4.5 架构链路

当前可接受的主链仍是：

```text
携程/美团渠道事实
  -> 酒店、平台、门店、业务日期、来源、质量状态
  -> 收益分析
  -> 授权后的 AI 判断
  -> 运营动作与通知
  -> 投资分析
```

关键边界：

- OTA 层不生成全酒店事实。
- PMS/订单事实缺失时，收益层不得反推完整收入。
- AI 层不绕过查看/执行权限。
- 通知层的“已保存”“HTTP 成功”“已送达”必须分开。
- 投资层只能消费定义清楚、范围一致的指标。
