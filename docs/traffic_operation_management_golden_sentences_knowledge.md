## 吸纳后的统一决策合同

截图中最有价值的不是孤立“金句”，而是一条可以进入宿析OS的经营判断链：

```text
同门店 + 同平台 + 同需求日 + 同指标口径
-> 曝光 -> 浏览 -> 订单 -> 销量/入住 -> 房费收入 -> 贡献利润
-> 定位泄漏环节
-> 选择一个对象、一个日期、一个变量的小步实验
-> 绑定基线、目标、保护线、止损、回滚和复盘
```

所有输出必须分开：

1. `facts`：当前门店、日期、平台和口径已经验证的事实。
2. `derived_metrics`：注明公式、分子、分母和输入来源的派生指标。
3. `hypotheses`：对房型、权益、政策、价格或流量来源的待验证解释。
4. `actions`：人工复核后的动作候选。
5. `guardrails`：底价、转化、收益、库存、止损和回滚条件。
6. `data_gaps`：缺少的底层定义、成本、订单、取消、入住或竞对证据。

## 可跨酒店复用的方法

### 1. 流量漏斗与价值兑现

- 曝光、浏览、订单是过程指标；房费收入、净收入和贡献利润才是结果指标。
- 高曝光或高浏览不能自动证明高收益，必须继续检查支付、销量、ADR、佣金、取消和房型结构。
- 浏览较强但订单或收入偏弱时，优先检查房型、权益、政策、价格和支付承接，不先把扩流列为唯一动作。
- 每个自然、活动或付费入口分别记录曝光、订单、房费收入、有效订单成本和边际贡献。
- 投流按高意向日期、剩余库存和目标价格定向配置，不平均撒向整月。

### 2. 指标语义不能互换

- 排名说明相对位置，份额说明市场占比，指数说明来源系统中的相对表现；三者不能互相替代。
- 平台转化率与自行粗算转化率必须保留各自分母、时间窗和去重规则。
- 销售、入住、取消和未来确定收入是不同事实；窗口差额只能标为待验证信号。
- 单周期数据不能写成趋势、同比或真实价格弹性。
- 商圈集中度判断必须保存 HHI 定义、样本、市场边界和周期；来源案例数字不直接成为通用市场结论。

### 3. 价格实验与房型角色

- 价格实验一次只改一个日期、一个房型、一个变量，并选择同需求日对照。
- 提价或降价都要先写销量容忍、收益保护、绝对转化保护、库存保护、停止和回滚条件。
- 没有每间夜变动成本、佣金和权益成本，不能声称利润改善。
- 引流房限量承担入口；主销房承担规模；升级房承担价值；套餐房承担客群。房型、价格计划、套餐和渠道库存不得混写。
- 高峰日期按剩余库存和 Pickup 调整，避免用最低价提前覆盖全部库存。

### 4. 运营管理动作

- 管理语言不能替代数据判断；每个动作同时写基线、目标、保护线、止损、回滚和复盘时间。
- 数据质量先于经营判断，指标口径不清时先补数。
- 周复盘固定输出 `保留 / 优化 / 停止 / 扩大` 四类清单。
- 团队评价看同需求日完整漏斗，不以单日排名奖惩。
- 业主价值以可持续收益和利润衡量，不以订单数最大化衡量。

## 系统检索与使用边界

- 通用方法进入 `knowledge_units`、`knowledge_chunks` 和员工 `knowledge_base`，可用于流量诊断、收益分析、建议卡和运营复盘。
- 两组原文目录以 `scope=case_reference` 保存，案例键分别为：
  - `jiuyide_traffic_flow_funnel_2026_07_29`
  - `jiuyide_operation_management_2026_07_29`
- `RevenueOperationsKnowledgeService` 默认排除案例；只有显式传入匹配 `case_key` 才返回。
- 默认 OTA Prompt 同样排除 `case_reference`，防止具体排名、金额、指数和门槛跨酒店套用。
- 知识不直接触发 OTA 改价、关房、开房、库存或投流写入；所有动作先进入人工复核。
