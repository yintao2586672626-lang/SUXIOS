# 宿析OS产品与协作宪章

> 版本：`v1.4`
> 生效日期：`2026-08-02`（Asia/Shanghai）
> 状态：`active`
> 变更理由：在不改变当前交付主线的前提下，加入“全量留存、分层记忆、分级使用”的经营记忆原则。

## 一、长期目标

宿析OS要成为真实可用、长期演进、节省酒店经营者时间的经营数据与研判系统。

系统持续打通：

`真实经营数据 -> 经营检查与报告 -> 系统AI研判 -> 人工决策 -> 运营执行与复盘`

当前阶段第一交付主线是：

`真实携程/美团 OTA 数据 -> 收益分析 -> 运营管理`

AI研判和投资辅助是下游能力，只在当前功能确实需要时接入，不作为数据、页面或运营前序功能落地的默认门禁。

当前优先级始终是：

1. 功能真实可用；
2. 数据稳定、可追溯；
3. 没有明显错误；
4. 用户能够理解结果、找到依据并完成实际工作；
5. 在不破坏真实性的前提下持续降低操作和沟通成本。

## 二、系统角色与决策边界

宿析OS是经营检查、经营报告和辅助研判系统，不是替用户发言或自动经营酒店的系统。

- 系统负责提供来源清楚、日期明确、酒店绑定正确、可回查的数据事实。
- 系统AI负责基于已验证事实给出研判、可能解释、风险和验证办法。
- 用户、老板、运营人员和行业专家保留观点表达、最终判断与行动决定权。
- 未经明确授权，系统不得自动执行OTA改价、投放、库存调整或其他生产操作。
- 竞对信息用于本店异常诊断和参考，不作为首页默认主线，也不自动决定本店价格。

## 三、事实、AI研判与未知

所有经营输出必须区分以下层级：

1. **来源事实**：来源、酒店、平台、目标日期、采集时间、保存和回读均可核验的数据。
2. **派生指标**：由明确公式和已验证输入计算出的结果，必须保留输入与口径。
3. **系统AI研判**：基于事实和派生指标形成的解释或建议，不等于事实或专家结论。
4. **缺口、冲突与未验证**：缺少字段、口径不一致、来源冲突、日期不匹配或尚未回读的状态。

每条重要AI研判应尽量说明：

- 依据了哪些事实；
- 适用酒店、平台、日期和经营范围；
- 把握程度或证据强弱；
- 仍缺少什么；
- 用户可以怎样用可理解的方法验证。

数据冲突时：

1. 先核对酒店、平台、日期、字段口径和来源批次；
2. 对可重新获取的数据执行受控重抓或补抓；
3. 重抓后仍冲突，保留双方原始证据和冲突状态；
4. 停止基于冲突项继续生成确定性AI研判，不用默认值、旧数据或话术消除冲突。

### 3.1 经营记忆原则

宿析OS把经营记忆作为现有经营闭环的支撑能力，不把它改造成新的产品主线。当前交付主线仍然是：

`真实携程/美团 OTA 数据 -> 收益分析 -> 运营管理`

经营记忆遵循“全量留存、分层记忆、分级使用”：

1. **事实记忆**：保留原始事实或其不可歧义的来源引用，并记录酒店、租户、平台、业务日期、来源、采集与回读状态。
2. **分析记忆**：保留规则或AI形成的诊断、解释、假设、证据强弱和待验证项；不得改写为来源事实。
3. **决策记忆**：保留人的确认、否决、调整、理由、责任人与适用范围；系统建议不自动等同于人的决定。
4. **执行与复盘记忆**：保留实际动作、执行证据、观察窗口、结果状态、失败原因和同口径复盘；变化信号不自动证明因果。
5. **SOP记忆**：只把经过复盘和人工确认的稳定做法升级为候选或已验证SOP，并保留版本、适用条件和反例；单次成功不得直接成为跨酒店标准。

“全量留存”指在授权范围内完整保留有经营价值的事实、分析、决定、执行、复盘及其版本关系，不包括密码、Cookie、令牌、完整浏览器Profile、无必要的客户隐私或其他受保护凭证。经营记忆优先保存对既有事实和证据的引用，不复制一份失去来源身份的“新事实”。

“分级使用”必须把保存、检索和使用分开：

- `仅归档`：缺证据、存在冲突、已过期或尚未回读，只能追溯，不进入结论或建议。
- `参考`：身份和来源可追溯，但证据仍不完整，只能辅助人工判断。
- `决策支持`：关键事实、酒店、平台、日期、口径和回读已核验，可以在相同适用范围内支持研判。
- `SOP模板`：已经多次复盘、人工确认且适用条件明确，仍需在具体酒店和日期重新校验后使用。

任何层级在被检索后，都必须再次检查租户与酒店权限、平台和日期范围、质量状态、冲突、失效时间及当前事实是否已变化。低可信记忆可以被保存和展示，但不得因为“已经记住”就获得更高使用权限。

## 四、首页与时间口径

首页围绕自家门店经营事实组织：

- **昨天**：默认主线，展示已经形成的经营事实、异常和需要处理的问题。
- **今天**：只展示当前已经取得的过程状态，不把进行中数据写成日终结果。
- **未来**：只展示明确标注为预测、情景或AI研判的内容。
- **竞对**：仅在本店表现异常或需要诊断时作为参考，不取代本店经营主线。

OTA数据只代表对应渠道。全酒店收入、OCC、RevPAR等指标需要PMS、CRS或其他全酒店来源和可验证分母。

- PMS能够稳定接入时优先接入；
- 暂时不能接入时，不强迫门店每天重复手填；
- 允许通过规范导入补充全酒店数据；
- 未获得全酒店数据时，继续使用OTA渠道口径并明确范围。

## 五、报告、语言与信息分层

- 默认使用中文，面向普通用户提供结果导向、可执行且容易理解的表达。
- 外部平台、标准、产品或技术专名确有必要时保留原文。
- 普通用户优先看到事实结果、异常、AI研判、缺口和下一步。
- 管理员可以查看完整数据来源、绑定、质量状态、内部诊断与排障信息，但仍不得展示Cookie、令牌、密码、完整Profile或客户隐私原文。
- 内部方法、SOP、提示词、工具组合、模型成本、客户资料和安全细节不向普通用户或对外报告暴露。
- 数据状态不得只靠文案表达；接口和持久化结果中必须保留机器可识别的事实层级与质量状态。

## 六、新酒店、账户与采集责任

新酒店启用必须形成：

`用户账户 -> 可访问门店 -> 系统酒店ID -> 平台酒店/POI -> 实际酒店名称或授权链接`

- 展示名称必须与实际酒店和授权页面对应，禁止错店或串店。
- OTA登录、验证码、Cookie、Profile和其他敏感登录信息由用户在自己的电脑本地完成和保存。
- 遇到登录失效、账号选择、密码、验证码、Passkey、短信或两步验证时暂停，让用户在原设备自行完成；不得索取或要求传输密码、Cookie、验证码或恢复码。完成后从最后已验证位置继续。
- 中心服务只保存必要的账户/设备/门店绑定状态、任务状态、失败原因和结构化业务结果。
- 不把所有酒店的抓取登录态集中到管理员电脑，也不集中保存所有门店浏览器Profile。
- 用户侧采集失败时，优先给出中文失败阶段和下一步；安全且可恢复的情况允许在同一授权设备上进行有次数上限的自动重试或补抓。
- 重试仍失败时保留真实状态，并提示联系管理员；不得切换到其他用户或其他酒店数据伪装成功。

## 七、原始数据、整理数据与覆盖规则

- 原始数据和整理后的标准事实都应保留，并建立可回查关联。
- 业务默认使用同酒店、同平台、同日期下最新且最完整的可信结果。
- 字段更少、证据更弱或质量更低的数据不得覆盖更完整结果。
- 完整度相同但关键字段冲突时，先重抓或重新核验；仍冲突则保留版本并标记冲突。
- 空值、旧数据、默认值、其他酒店数据和历史快照不得伪装本次真实成功。
- `saved_count`、页面出现数据或接口返回成功不能单独证明数据可用；必须继续验证保存身份和数据库回读。

## 八、未完成页面与演示数据

- 未完成页面可以展示，但必须让用户知道哪些操作尚不可用或仍在建设。
- 演示数据可以用于帮助理解页面和流程，界面不必在每个数值旁重复增加醒目标识。
- 演示数据在底层数据契约中仍必须保持 `demo`、`synthetic` 或等价身份。
- 演示数据不得写入真实经营快照、不得参与真实AI研判、不得生成可执行运营建议，也不得冒充真实采集成功。
- 当演示内容可能被普通用户误解为本店实时事实时，页面必须提供一次清楚、不过度打扰的范围说明。

## 九、开发协作方式

用户提出业务想法时，Codex应主动补全目标、数据来源、业务口径、用户入口、保存回显、失败状态和验收方式，尽可能交付完整、稳定、可用的版本，而不是用敷衍的占位MVP代替真实闭环。

用户通常只会用口语说明“这里有问题”“怎么改”或“想要什么”，也可能只提供截图、当前页面、任务上下文或局部片段。助手必须主动结合项目现状、当前界面、已有历史、业务链和安全/可逆性检查，推断目标门店、日期、数据范围、功能入口与验收方式；不得因为描述不够技术化或不够精确就停工、把实现细节推回用户或反复追问。只有不同选择会实质改变结果、触及本宪章定义的高风险边界，或关键信息确实无法从现有上下文查明时，才提出一个最小且决定性的问题。

用户明确提出当前业务目标并要求“继续”“执行”或“完善”后，该指令视为当前闭环内本地实现和聚焦验证的一次授权。当前目标已经明确包含指定环境发布、生产验证、可回退迁移或必要写入时，同一次授权覆盖对应流程，不得要求用户复述固定授权句式，也不得逐步骤重复确认。提交、推送和外部PR只有在本次请求明确要求保存或发布到GitHub等远程目标时才执行。

默认可以直接执行：

- 阅读、诊断和证据核对；
- 需求范围内的可逆代码修复；
- 明显缺陷的最小修复与相关测试；
- 不触碰真实业务数据的fixture、静态守卫和契约验证；
- 保持旧功能兼容的局部整理；
- 当前目标已经明确包含时所需的可回退数据库迁移、指定环境发布、生产页面验收和已明确目标的测试写入。

只有以下信息或动作尚未被当前指令覆盖、且不能从现有上下文安全查明时，才提出一个最小且决定性的问题：

- 真实外发对象、目标租户、门店或数据范围不明确；
- 需要用户新输入账号凭证、密钥或敏感数据；
- 删除或覆盖用户内容，或执行不可逆数据库操作；
- 改动已稳定的核心业务规则或数据口径；
- 工作范围相对当前目标发生实质扩张；
- 本次请求未明确包含的提交、推送、外部PR、部署、生产写入或正式外发。

当真实账号、生产数据库、消息或外部系统写入、正式发布已经属于当前明确目标，Codex应执行并验证，不再重复索要授权；真实外发目标缺失时不得臆造接收方。

多项工作可以并行，但必须满足：

- 文件和业务边界互不冲突；
- 同一核心模块、数据库迁移、鉴权或真实数据链保持单一写入者；
- 有冲突的工作排队处理，不并行抢写；
- 每项工作独立完成“实现 -> 验证 -> 状态回报”闭环；
- 不用并行制造重复扫描、重复任务或无法归属的工作区差异。
- 写入前检查实际仓库和目标文件的 Git 状态与差异；工作树不要求全局干净，也不得为开始任务而清理现有改动。保留用户和并发任务的无关修改，目标文件存在无法安全合并的重叠时只提出一个决定性问题。

### 9.1 责任分工、单主线与优先级

- 用户负责业务目标、重大产品方向和外部、敏感、不可逆操作的权限边界；Codex负责把业务语言转成技术范围，自主完成实现选择、验证、故障恢复和结果交付。不得让用户承担技术项目经理、测试员或不同工具与专家之间的传话工作。
- 功能实现是第一目标。计划、审查、测试、证据整理、文档、安全、治理和发布只用于支持当前功能，默认做到与改动风险直接相关的最小程度；普通功能不得先扩成全仓审计、完整门禁或发布工程。
- 默认保持一个主目标、一个可验收结果，同一业务目标的在制工作数量为一。只有任务确实独立、写入边界不冲突且并行收益明确时才拆分；协作人数增加不改变单一业务结果的责任归属。
- 选择工作方向时，按业务发生频率、对产品链的阻断程度、可取得证据、预期经营影响和闭环成本排序。用户询问“先做什么”或“今天优化什么”时，先给一个最佳方向，不用全仓审计、功能数量或未排序清单代替决策。
- 当前文件、运行环境和证据没有变化时，复用最近一次已经验证的事实；只有证据可能过期或相关状态发生漂移时才定向复查，不从头重复扫描。
- 连续三轮定向检查仍没有新增决定性证据时，停止继续分析，转入最小安全实现、缩小范围，或报告唯一真实阻塞。

### 9.2 功能完整性补全

用户提出的通常是业务结果，不会逐项列出所有技术细节。只有缺失后会直接阻止用户完成当前功能的部分，才属于应主动补齐的功能本体：

1. 用户能够找到并进入当前功能；
2. 完成主要动作所需的必要输入校验和权限边界；
3. 真实的成功、失败、缺失或部分完成状态；
4. 业务确实需要持久化时的保存、回读和回显；
5. 被修改路径的旧行为兼容和一个聚焦验证。

这些属于“功能完整性补全”，不是扩大需求。编辑、幂等、恢复、诊断、治理或其他增强只有在当前功能确实依赖时才加入；否则与重构、新页面、新指标和下一阶段设想一样留待后续。

### 9.3 用户可见的最短安全路径

- 衡量功能进度时，优先看用户取得第一个可信结果需要多少步骤、等待和人工转换，而不是看改动文件数、代码量或内部任务数量。
- 在不降低数据真实性、权限隔离和可恢复性的前提下，减少重复录入、手工复制、页面来回切换、不必要的后台排队和中间人交接；能够在当前入口直接返回结果时，不把用户默认送入任务列表等待。
- 优先复用已经验证且身份一致的数据和上下文，不让用户重复提供系统本可安全取得的信息；未经验证的默认值、推断或跨日期数据不能以减少操作为理由自动填入。
- 每个新功能都应明确它替用户减少了什么工作、缩短了什么决策时间，或闭合了产品链上的哪个断点；无法说明时先缩小功能，而不是继续堆界面或配置。

### 9.4 最小验收与停止条件

默认执行顺序是：

`最小相关理解 -> 直接实现功能 -> 聚焦验证主路径 -> 有页面或交互时实际打开 -> 报告结果并停止`

- 普通功能的最小验收只确认：入口可找到、主要动作可执行、需要保存时能够回显、关键失败不伪报成功，以及至少一个与改动直接相关的检查通过。
- 只有当前目标直接涉及真实账号、外部投递、生产写入、跨酒店/租户、不可逆数据、关键收益公式或发布，才扩大到相应的真实环境、负向边界或全量门禁；不得因为仓库存在大量测试和审查工具就默认全部运行。
- 代码、本地页面、真实账号、生产启用和经营效果仍要如实区分，但这些状态用于防止夸大，不代表每个功能都必须取得全部层级证据后才能交付。
- 外部专家、其他项目或报告只对实际采纳的部分做必要核对，不启动额外的全面评审链。
- 当前功能达到用户要求后立即停止。可选增强只记录，不自动演变成重构、全仓审计、发布治理或下一阶段开发。

### 9.5 经营动作与效果复盘

- 经营效果复盘只在当前功能目标本身包含AI建议、运营执行或效果跟踪时进入验收；数据采集、页面回显或其他前序功能已经实现时，不得因尚未形成次日或七日效果而阻止该功能交付。
- 可以转成运营动作的AI建议应尽量带有事实基线、目标指标、建议理由、责任人、执行期限或观察窗口、执行证据和复盘状态；缺少这些条件时标记为分析建议，不伪装成已经闭环的运营任务。
- 推荐的高价值日常闭环是：`昨日 OTA 事实 -> 本店与商圈或同行的同口径对比 -> 一个主要漏斗瓶颈 -> 一个今日动作 -> 次日执行检查 -> 七日效果复盘`。
- 次日或七日数据尚未形成时使用“继续观察”或对应未验证状态，不用旧日期、其他门店、其他平台或模拟结果制造ROI和因果证明。
- 复盘时保持酒店、平台、日期口径、指标定义、动作对象和参考范围一致；相关变化只能作为效果信号，不能自动证明唯一因果。

## 十、沟通与过程可见性

- 重要问题输出：结论、关键证据、技术原因和剩余风险。
- 面向经营决策时优先按“结论 -> 证据状态 -> 业务影响或风险 -> 建议动作 -> 负责人/进度 -> 投决影响”组织；金额影响没有可靠口径时明确未知，不强行估算。
- 普通事项保持简洁，避免长篇背景和重复说明。
- 工作过程持续显示当前状态：`阅读`、`修改`、`测试`、`等待`、`完成`。
- 过程更新必须包含新里程碑、新证据、状态变化或真实阻塞，不重复发送没有信息增量的“仍在处理中”，也不让用户承担工具、专家或不同任务之间的传话。
- 已完成、已验证、未验证、部分完成、外部阻塞必须分开表达。
- 测试通过不等于真实OTA、生产发布或业务效果已经完成。
- 如果用户想法与已验证事实、长期产品目标或安全边界冲突，应明确指出冲突与后果，不通过迎合产生假成功。
