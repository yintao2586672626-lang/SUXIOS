## 五、下一次真实试用的验收方案

建议使用已授权的单酒店、单渠道、固定业务日数据，在经营问答中验证：

1. **能查准**：明确的指标查询与数据库同范围读回一致，避免不必要的模型调用。
2. **能解释**：分析请求列出事实来源、缺失项和一条可复核建议；不把相关性表述为因果。
3. **能拒绝**：无事实、日期不符、别的酒店、工具失败、字段缺失时，状态与原因准确。
4. **能保存**：页面生成、保存、按 ID 读回、刷新后的文本和引用一致。
5. **能度量**：记录事实正确率、错误放行次数、人工修改量、完整任务耗时和复核时间；收集供应商 Token/用量回执与计价版本后，再计算总费用。

扩大使用的依据应是同一组任务与人工基线的对比。当前不设置未经验证的降价幅度、经营收益目标或全酒店效果结论。

## 七、继续自主优化：调用用量与兼容边界

### 用户能够看到的变化

入口：本机系统的 **AI 治理 → 调用日志 → 详情**（沿用原有超级管理员权限）。

- 列表新增总 Token 与本条供应商调用耗时；详情展示输入、输出、缓存命中、有效回执数量和重试后的已知小计。
- 区分“完整用量”“部分请求缺少用量”“无有效用量”“未调用模型”和“旧记录未保存用量”。真实的 0 保留为 0，缺失项显示未知。
- 费用显示“未知：尚无已核实的计价依据”。缓存命中和推理 Token 是输入/输出的组成部分，不再额外加到总 Token 上。
- 供应商切换分日志记录，包含重试的耗时单独计量；原有 `latency_ms` 是从整次请求开始累计到该日志的时间，不能跨日志相加当作任务耗时。

### 实现与数据边界

1. 新增 `LlmUsageObservation`，只解析供应商响应外层 `usage`，不相信模型正文自称的用量，不以字符数推算 Token。
2. 验证非负整数与 `输入 + 输出 = 总量`；不一致回执排除并显示无效数量。重试期间缺少任何有效回执，完整总量保持 `null`，另外提供已知部分。
3. `LlmClient` 将观测保存在现有 `governance_json.usage_observation`，版本 `llm_usage.v1`；无需数据库迁移。每条记录仅含当前供应商本轮尝试与重试，不重复累计之前的供应商。
4. HTTP 失败或结构化内容不合格仍保留供应商已返回的消耗。缓存回退新记录不继承旧 Token；幂等重放复用原日志 ID，不新增计费记录。
5. `AiGovernance` 的列表与详情输出同一份已保存字段；旧记录以 `legacy_unknown` 回显。未修改任何真实业务事实或历史日志。
6. 结构化输出修复：`anyOf` 优先保留原业务分支允许的显式 `null`，分支试探使用独立对象；对象枚举按 JSON 语义比较，保留数组/对象、布尔/数字的区别。
