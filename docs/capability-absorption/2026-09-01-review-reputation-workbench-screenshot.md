## 宿析OS适配边界

1. 只读取当前酒店、所选日期范围内 `online_daily_data` 的 `review` 聚合记录。
2. 携程、美团以及携程来源内附带渠道保留各自原始评分与渠道身份；不计算跨平台平均分。
3. 只使用通过现有事实质量门的行生成分数、点评量、低分/差评量和趋势；未验证行不覆盖已验证结果。
4. 累计点评量较前次回退时标记需要重新建立比较基线，不伪造新增量。
5. 不展示点评正文、住客身份、手机号或匿名身份匹配结果；处理动作继续进入既有隐私受限的点评证据入口。
6. 当前未接入的抖音、飞猪不显示假卡片；取得真实采集、保存与回读证据后再扩展。

## 验收

- 正常样例：同一酒店存在已验证的携程/美团点评聚合时，按平台显示最新原始分、点评量、低分/差评量及最多 7 个业务日趋势。
- 边界样例：携程来源内含去哪儿等附带渠道时，作为来源内渠道展示，不与携程主口径混算。
- 失败样例：只有未验证行或完全缺数时，分数和数量保持 `—`，页面显示未验证/缺失状态，不使用截图演示值或 0 补齐。
- 停止条件：本地汇总合同、页面入口、既有处理入口和聚焦回归验证通过；不扩展采集平台、预测算法或外部点评操作。

## 正式晋级的经营机制

用户随后明确授权“真正对宿析有用的，可以吸纳进去”。筛选后只晋级一条独特且可复现的机制：`点评事实 → 注意力排序 → 现有每日一件事审批与复盘`，没有新建第二套口碑任务系统。

接入合同：

```text
同租户 + 同酒店 + 携程/美团 + 目标业务日
→ online_daily_data 点评聚合精确回读
→ 仅识别三类确定性信号：
   1. 未回复点评数 > 0
   2. 相邻业务日低分/差评累计数增加
   3. 相邻业务日平台原始分下降
→ 作为 strict_fact_signal 进入 daily_one_thing.v2
→ 与数据缺口、已保存问题按影响/紧迫/证据/成本统一排序
→ 每天仍只选一件，状态保持 draft / pending_approval
→ 用户人工批准后才可进入原执行任务；回复、申诉和外部平台写入仍需用户主动触发
```

未晋级内容：单独的差评任务表、自动回复、自动申诉、匿名住客识别、跨平台综合分、竞对点评推断、评分预测、抖音/飞猪假接入。口碑信号只分配注意力，不声明原因、收益或处理效果；自然事实未到时复盘继续保持等待。

本机真实只读回放使用酒店 `80`、业务日 `2026-07-18`：美团当前行 `online_daily_data#50410` 通过严格回读，但相邻前一业务日没有严格点评基线，且当前没有未回复/差评增加/评分下降信号，因此 `ota_reputation_daily_signal.v1` 返回 `no_actionable_signal`。接入后的 `daily_one_thing_input.v1` 仍只产生原有 `gap:ctrip:target_date_source_rows`，最终选择保持 `explicit_data_gap`，`can_execute=false`、`external_write_performed=false`。这证明口碑只在有确定性异常时参与排序，不会为了展示新能力制造事项或覆盖更重要的数据缺口。
