## Codex 使用适配（2026-09-01 复核后）

后续复核确认，指南中“先说结果、按任务路由、固定方法再复用、复杂度由系统承担”的机制同样适合帮助别人使用 Codex 维护宿析OS。宿析OS不照搬豆包的工作任务、Skill、伙伴或小队名称，而把它压缩为一个面向普通用户的协作合同：

1. 用户只说明一个可验收的业务结果。
2. 只补充会改变结果的门店、平台、日期和允许动作。
3. 交付物和验收条件必须明确；文件、框架、命令和内部分工由项目处理。
4. 本地实现、自动验证、Git、部署、现场与经营效果分别报告，前一层不证明后一层。

该合同已作为 `codex-collaboration` 主题接入全局“宿析精准查数/系统助手”，并加入“怎么让 Codex 帮我？”快捷问法；精准查询词典会把 Codex 协作问法确定性路由到该主题。边界明确保留：检查或诊断不自动授权修改，本地修改不自动包含提交、推送、部署、OTA/PMS写入、外部发送或审批。

当前证据上限：本地源码已修改；Codex 协作主题与下述任务蓝皮书 V1 已通过聚焦后端、前端和构建验证。本机运行资源返回 HTTP 200 并匹配最终资源指纹；未登录调用系统助手返回 401。Playwright 到达本机宿析OS登录页，但没有安全自动填充，因此尚未完成登录态下的真实点击目视验收；也未提交、推送、部署或取得真实用户使用证据。

## 宿析OS任务蓝皮书 V1（2026-09-01 本地候选）

本次把来源中的“按任务找方法、每一步可验收、失败就明确停住”吸收到宿析OS既有入口，而不是另建一套静态说明书。首版只保留三个高频、能产生实际结果的用户旅程：

| 用户任务 | 真实入口与路径 | 完成标准 | 明确边界 |
| --- | --- | --- | --- |
| 今天先做什么 | 全局助手/知识中心 → `经营机会` → 每日一件事 | 唯一事项已保存并精确回读；运行 ID、待审批意图一致；执行任务数与外部写入数为 0 | 只形成 `pending_approval`，未经人工审批不执行 |
| 数据为什么没进来 | 全局助手/知识中心 → `数据健康` → 自动采集 → 运行监控 | 定位到酒店/平台/日期及身份、采集、保存或回读中的真实失败阶段；成功时取得当前范围严格回执 | 不用 0、旧日期或其他平台补位；账号无数据中心权限时明确无入口 |
| 从可信数据生成日报 | 全局助手/知识中心 → 数据健康 → AI 经营日报 | 严格事实通过门禁；可信播报保存并精确回读；复制与朗读使用同一保存文本 | 不自动采集、不写 OTA/PMS；同一可信快照的企业微信外发尚未闭合，本版不把通知中心算作完成步骤 |

三条任务已加入全局助手快捷问法和确定性路由，活动路线可在本地恢复，“继续当前任务”优先出现。知识中心突出三张核心卡，同时保留原有任务卡；数据健康卡按当前账号可见菜单降级，没有权限时显示“当前账号暂无数据中心入口”，不直接绕过菜单。

本地验证证据：

- `SystemUsageAssistantServiceTest` 与 `PreciseQueryRouterServiceTest`：49 项、420 个断言通过；三条自然语言均由确定性目录路由，`external_llm_called=false`。
- 任务蓝皮书、知识中心、经营机会、模板和资源指纹相关 Node 测试：39 项通过。
- 前端模板、启动帮助器和公共入口验证全部通过；公共入口启动体积仍在目标内。
- 本机健康检查 HTTP 200，应用、数据库和 209/209 数据库版本均正常；运行模式为 `development_fallback`，不能当作生产部署证据。
- 最终全局助手资源和知识中心生成资源均以 HTTP 200 返回，且资源哈希与页面版本参数一致；登录态点击仍待原设备安全登录后复验。

### 1. 豆包任务路由

| 任务形态 | 建议入口 | 使用边界 |
| --- | --- | --- |
| 临时问答、改写、小范围整理 | 普通工作任务 | 给定材料范围和交付格式 |
| 同一流程会反复执行 | Skill | 先用普通任务跑通，再固化；安装前审查来源、脚本和权限 |
| 一个专业角色负责到底 | 工作伙伴 | 先做数据/文件质量检查，交付新文件，不改原件 |
| 多角色且存在前后依赖 | 工作小队 | 先展示分工、输入、交接和总复核人，再开工 |
| 重复、规则稳定、结果易验收 | 定时任务 | 先手动成功；缺来源时失败关闭；不自动付款、发布或删除 |

### 2. 统一任务合同

给豆包的任务至少写清七项：

1. 目标：最终要得到什么，不只写“分析一下”。
2. 材料：允许读取的文件、知识库、链接和时间范围。
3. 事实边界：哪些结论必须来自材料，哪些内容不得补写。
4. 交付物：文件类型、结构、数量、输出位置和负责人。
5. 失败状态：来源不足、字段缺失、冲突或权限不足时怎样停止并回显。
6. 动作边界：不改原文件、不外发、不发布、不删除、不执行真实经营动作。
7. 验收：数字复算、来源回链、版本/日期检查和待确认清单。

可直接用于豆包的模板：

```text
目标：完成【一个明确交付物】。
材料范围：只读取【文件、飞书文档或公开链接】；时间范围为【】。
事实边界：关键数字和判断必须回到材料或一手来源；冲突并列，缺失标记“待确认”，不要补写。
交付：生成【格式】新文件，包含【必要章节】和验收清单。
动作边界：不修改原文件，不发送、不发布、不删除，不登录或操作 OTA/PMS。
失败处理：资料、权限或来源不足时停止正式结论，返回缺口和唯一补充项。
验收：列出来源、版本/日期、复算结果、未确认项和实际生成文件入口。
```

## 推荐先跑的三个豆包样例

1. **会议材料闭环**：把一段脱敏会议内容整理成结论、待办、负责人、截止时间、风险和未决项；缺负责人或日期时保留待确认，不自动发送。
2. **Office 新文件交付**：读取一份非敏感 Word 或 Excel，先检查结构和数据质量，再生成新的摘要/PPT/分析文件；原文件保持不变。
3. **飞书知识回源查询**：在账号确实拥有权限时，查询一条制度或 SOP；答案必须带文档名、版本、生效日期和出处，冲突或缺失时指向负责人，不替其审批。

只有三个样例中至少一个能稳定重复成功，并覆盖一次权限不足、来源缺失或冲突状态，才考虑把该流程制作成豆包 Skill。

## 与宿析OS现状的差异判断

指南提出的来源、时效、冲突、负责人和人工确认机制，宿析OS已经具备：知识单元有复核到期和证据等级，正式知识有门店隔离、审核人、审核期限、不可变修订、批准/退回事件与人工晋级台。因此本次没有新增知识中心字段、治理页面或自动化；只在既有全局系统助手与确定性查询入口中增加 Codex 协作主题，避免重复建设另一套入口。

真正尚未验证的是“豆包在当前账号与当前版本中，是否能稳定完成上述三个个人办公样例”。该验证需要用户主动打开豆包并授权相应材料；在此之前，本卡保持 `reference_only`，不进入酒店事实、收益结论或自动经营动作。
