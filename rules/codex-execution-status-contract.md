# Codex 执行与状态模子

这是宿析OS日常开发的单一执行与汇报口径。其他规则出现重复或冲突时，本文件优先决定任务怎么推进、怎么验证、怎么报告；业务真实性、权限和数据安全边界仍按专项规则执行。

## 1. 执行模子

```text
明确范围 → 完整实现 → 风险驱动验证 → 完整报告 → 验收后停止
```

1. 以用户本次请求为验收单位，明确范围、非目标、验收和停止条件。用户要求全项目扫描或完整清单时，先列出全部范围并按模块推进，不能自行缩成一个局部修复。
2. 分析、调研、方案、初稿、评审或测试只有在结果会改变决定时才做。
3. 完成需求内的正常、失败、兼容、恢复及保存回读路径；按实际适用性检查，必要依赖不算越界。普通技术问题自主修复，难点按 `quality-completeness-and-issue-handling.md` 说明证据、影响和建议；未经请求不扩成无关重构、业务决策或外部执行。
4. 完成前检查是否还有遗漏的验收项。全部适用验收通过或真实阻塞已说明后报告并停止；单条测试通过不是整个功能完成，没有新证据或风险时不重复同一检查。

## 2. 验证模子

以下为起点而非上限。以真实影响面和未解决风险决定验证深度，不因追求最少命令、省额度、固定次数或清单未列出而省略必要检查。

- **简单修改**：对应模块测试 + 必要语法或类型检查。
- **复杂修改**：涉及模块测试 + 直接依赖模块测试。
- **广泛影响**：大型/核心重构、依赖范围无法可靠界定、明确全量验收或适用环境要求时运行完整测试套件；全项目扫描也可按覆盖矩阵分组验证并明确未跑部分。
- commit、PR、发布候选、文件数量或“重要”标签本身不升级验证等级。
- 同一未变化产物复用已有证据；伞形命令覆盖的子检查不重复运行。失败后只复验失败项、修改项和直接依赖，除非影响面扩大。
- 测试、页面/API、保存回读、GitHub、部署和现场结果是不同证据，不能互相冒充。

## 3. 状态模子

涉及修改时必须给出一行状态，不再只说“完成”：

```text
状态：实现<状态>｜验证<状态>｜Git<状态>｜部署/现场<状态>｜阻塞<状态>
```

允许值：

- 实现：`无修改`、`已修改`。
- 验证：`未验证`、`聚焦通过`、`集成通过`、`现场通过`、`失败`。
- Git：`不适用`、`未提交`、`已提交未推送`、`已推送`。
- 部署/现场：`不适用`、`未部署`、`已部署未现场验证`、`现场已验证`。
- 阻塞：`无`，或真实阻塞摘要；多个阻塞分项列全，未知就写 `未知`。

示例：

```text
状态：实现已修改｜验证聚焦通过｜Git未提交｜部署/现场未部署｜阻塞无
```

## 4. 默认回复模子

普通修改优先采用以下摘要；审计、跨模块任务和多个问题必须补充完整清单与证据，不能用模板省略用户所需结果：

```text
结果：一句话说明用户现在得到什么
状态：实现…｜验证…｜Git…｜部署/现场…｜阻塞…
改动：只列当前任务的关键改动
验证：只列实际运行及其结果；未运行不写成计划
下一步：当前最优先的下一步；多项独立问题在清单中各写下一步，当前闭环结束则写“停止”
```

手机端先给简短摘要，详细清单放在后文或可点击报告；不设会遗漏验收要点的硬性行数限制。过程更新只说新证据、真实阻塞或下一动作，不重复背景和已报告内容。

## 5. 项目修改总账模子

盘点整个项目时先只读建立基线；用户授权处理普通问题后，可逐项复现、修复和验证。保留已有改动，不清理、不重置、不自行提交。按业务目标分组，不按每个文件堆清单：

| 修改组 | 来源/负责人 | 实现 | 验证 | Git | 部署/现场 | 唯一下一步 |
|---|---|---|---|---|---|---|

- 来源只使用：`当前任务`、`用户已有`、`并发任务`、`历史遗留`、`未知`。
- 没有当前证据就写 `未知`，不得从文件存在、测试通过或 HTTP 200 推断提交、部署或现场完成。
- 总账回答“现在在哪一层、还差哪些验收”；列全已确认缺陷、重要未验证项及真实阻塞，区分普通已处理问题与需要用户判断的难点。过程日志和完整 diff 链接到证据，避免挤占摘要。
