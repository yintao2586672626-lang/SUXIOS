# 完整交付与问题处理规则

生效：2026-09-07。适用于宿析OS活动工作树及其全部模块。用户本次明确要求、业务真实性和既有授权边界优先；本规则补充执行合同，不把普通建议变成新的审批流程。

## 1. 完整性的判断

- 以用户想完成的工作为单位，检查入口、操作、计算/处理、保存、精确回读、编辑或刷新、兼容、失败和恢复。只检查实际适用项，注明不适用原因；不能把“最小改动”理解为少做必要功能。
- 稳定性、性能、可维护性或安全问题一旦已经影响本次结果，就属于本次处理范围；未影响本次结果的优化如实登记，不自动扩成全系统重构。
- 用户要求扫描全部项目/模块时，先建范围清单。活动代码、冻结恢复目录、独立项目、外部云项目分别登记；历史工作树不重复算成新项目。范围未明确的其他目录不擅自修改。
- 每个模块分别记录已盘点、已读源码、已执行测试、已查页面/API、未运行和阻塞。不能把“目录扫过”“测试存在”或健康接口通过写成整个模块验收通过。

## 2. 普通问题直接处理，难点完整提出

| 分类 | 判断 | 处理方式 |
| --- | --- | --- |
| 普通技术问题 | 可复现或有确定合同，修复不改变业务口径和外部授权 | 自主定位、修复、回归并说明结果；不为常规技术选择反复询问 |
| 技术难点 | 多种根因、跨模块交互、兼容风险或证据互相矛盾 | 收集能区分假设的证据，比较方案并给推荐；能在授权内安全解决则继续，无须仅因难度高停下 |
| 业务取舍 | 指标口径、酒店/租户/日期范围、功能启停、成本收益或不可逆结果需要选择 | 提供具体可审阅方案、影响和推荐，集中提出确实会改变结果的问题；不让用户选择内部实现细节 |
| 外部阻塞 | 缺现场账号、数据、授权、服务或设备条件 | 完成不依赖该条件的工作，说明阻塞阶段、缺少的条件及解除后的验收；缺凭证时由用户在原设备处理 |

完整问题清单按“问题/证据/影响/已做工作/剩余验收/建议下一步”组织，不限于一个问题或固定条数。假设、风险和已复现缺陷必须区分，不为凑清单编造问题，也不把同一根因重复计数。

调查连续无新增证据时应改变方法、缩小假设或说明缺少什么；不以固定读取次数、时间或token目标自动放弃，不盲目重试到绿。

## 3. 各类模块验收重点

| 模块 | 需要关注的实际边界 |
| --- | --- |
| 携程/美团采集、历史与数据健康 | 酒店/平台门店/业务日/快照一致；采集、保存、精确回读分开；当前登录故障不抹掉有效历史；重试、重复提交、分页与过期请求；时间按实际时刻比较，明确上海业务日和带时区输入；历史截至时刻查询同时约束快照与事件的 observed_at，不使用当时尚未知的信息 |
| 收益分析、机会、财务与量化模拟 | 分子分母同范围同单位；汇总、差值、乘除运算后的结果也必须为有限数，有限输入不等于有限结果；不可计算返回明确状态、原因和 null，不能输出 INF/NaN 或补零；负库存等有效性判断在输出舍入前执行，金额计算不借用已舍入的展示数量；指标值、状态、原因贯穿接口、保存、回读和UI |
| AI报告、日报与经营问答 | 接收端验证请求与返回的酒店/租户/平台/日期范围；异常事实在落库前拒绝；数值来自可核对事实；报告生成、列表、按ID回读、复制/导出使用一致内容和版本 |
| 运营任务、周计划、开业与自动化 | 建议、待审批、已批准、已执行、已回读、已复盘和有效果分别记录；错误引用/跨酒店不能结案；复盘完成不等于改善，更不等于因果成立 |
| 门店管理、系统管理与AI配置 | 权限与酒店隔离；所有可写入口遵守同一约束，专用 PMS 绑定和旧配置入口均不得形成双启用来源；日期与回显依赖参数在写入前校验，参数失败不得留下已修改状态；修改后保存回显；脱敏；错误恢复；缺配置显式报错；新凭证、授权、外发与经营动作不自动执行 |
| 知识中心 | 来源、版本和适用条件可追溯；reviewed_at 不晚于决策截至时刻，未来复核记录不能放行当前决策或任务；reference_only与业务事实分开；新增、检索、修改和回读一致；不把参考材料直接升级为经营结论 |
| 数据库与历史迁移 | 冻结基线、已登记迁移源码及校验和保持可重放；隐藏或停用功能不删除其历史迁移，也不放宽 checksum 验收来掩盖缺文件；源码恢复、数据库执行、部署分别报告，实际迁移按既有授权边界执行 |
| 页面壳与前端入口 | 当前运行资源与活动源码身份一致；登录后真实挂载；加载顺序和错误可见；实际用户视口；静态页面通过不替代业务操作 |
| 冻结的策略、投决与生命周期入口 | 登记状态与隐藏边界一致；保留已有数据和恢复证据；扫描不包含自行解冻或宣称可用，启用需明确业务决定 |

同类规则是检查线索，不要求所有小修改跑完整矩阵。具体页面合同仍以 `business-page-contract.md` 为准。

## 4. 验证与远程交付

- 先用现有测试或针对性回归复现，再修复。测试覆盖不足时补充真实行为边界，不能仅检查代码中出现某个字符串，也不能为了通过而更改原本正确的验收标准。
- 修复后检查影响模块和直接依赖；必要时扩大到集成、页面和完整套件。验证深度由证据决定，最低检查不是上限，重复次数和总测试数也不是质量证明。
- 用户主要远程或手机操作时，先给自包含摘要，再给完整问题清单和可点击证据。不要把必要确认拆成多轮，也不要为了少打扰而隐瞒失败或擅自授权。
- 阻塞或跨会话时保存目标、现有改动、验证结果、未完成项和下一操作。验收结束后停止，后续业务阶段另行明确；交接文件本身不代表已安排自动续跑。
- 一般问题可直接修复并本地验证；提交、推送、PR、发布、真实OTA/PMS写入和对外发送仍需要范围匹配的明确授权。
