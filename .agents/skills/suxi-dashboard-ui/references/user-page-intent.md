# 宿析OS用户页面偏好参考

> 整理日期：2026-07-30
>
> 证据范围：2026 年 6 月和 7 月的宿析OS项目任务、页面截图反馈与用户纠正。

## 使用边界

这是帮助理解用户的偏好参考，不是硬性规则。

- 当前用户请求和当前页面事实优先于本文。
- 将本文作为高自由度启发，不机械套用，不据此限制 Codex 的方案空间。
- 不把历史偏好当作永久授权、禁止项或固定产品需求。
- 不因追求简洁而跳过必要的数据真实性、安全边界、验证或架构调整。
- 当更好的实现需要不同布局、更多操作、重构或新的验证方式时，Codex 可以基于实际情况采用。
- 只在相关问题出现时读取对应章节，不要求每个页面任务完整加载本文。

## 核心观察

### 结果优先

用户通常先看功能是否真的能用：能找到入口、完成操作、保存或回显，并得到真实业务结果。计划、代码量和测试数量不能单独代表业务完成。

这不表示可以跳过测试或工程质量；验证深度由改动风险和当前目标决定。

### 系统承担不必要的操作负担

用户往往希望系统利用当前门店、日期、已有配置和上下文减少重复输入。后台可以保持严谨，前台不必把每个内部参数都变成必填项。

这是一种常见偏好，不是禁止复杂配置。专业用户场景或高风险操作仍可展示必要选项。

### 高信号密度，而不是单纯极简

用户会要求详细数据、来源和深度分析，同时会否定重复字段、无效状态和过长文案。更准确的理解是：

- 保留会改变判断或动作的信息；
- 减少重复和没有当前用途的信息；
- 在需要时提供详情，而不是删除真实证据。

页面可以信息丰富，不要求固定卡片数量、字段数量或按钮数量。

### 经营视角

用户经常按酒店一天的节奏描述需求，例如计划、观察、异常提醒、定时播报和晚间复盘。设计页面时可以优先考虑经营任务是否连贯，而不必把后端模块结构直接暴露给用户。

具体页面仍可根据业务复杂度采用工作台、分步流程、多页导航或其他合适结构。

### 真实上下文

用户高度关注真实门店、业务日期、来源、当前选择和发送目标。页面、预览和结果通常应与当前上下文一致。

是否实时联动、何时刷新以及展示多少来源元数据，由具体功能和性能成本决定。

### 自动化与人工入口并存

用户倾向让重复工作自动运行，同时保留手动触发用于确认、补抓或异常恢复。

这不是所有功能都必须双入口。Codex 应根据频率、风险、成本和现有架构判断是否值得提供。

### 保护已经有效的部分

“方向没问题”“不要影响核心功能”“除了 X”等表达通常是在标记保留项和排除项。优化时应先理解哪些部分已经获得认可。

必要时仍可以重构或调整相邻模块，但应说明为什么这对当前结果有实质帮助，并保持兼容或可回退。

### 真实结果与技术验证分开表达

当用户指出“验证很多次还没成功”，通常意味着代码验证和真实业务结果没有闭合。适合把状态拆成：

- 实现或测试状态；
- 页面、数据回读或外部结果状态；
- 仍需用户或外部环境完成的事项。

不要建立固定证据等级；根据当前任务选择最有证明力、成本合理的验证。

### 详细程度随场景变化

- 审查、字段映射、复盘和方案说明可以详细。
- 日常经营页面和消息通常更适合直接、可扫读。

这不是绝对限制。复杂经营场景可以提供完整页面，简短报告也可以只给结论。

## 常见表达的可能含义

这些是理解线索，不是自动动作或授权。

| 用户表达 | 常见关注点 | Codex 保留的判断空间 |
|---|---|---|
| “方向没问题，但是复杂了” | 希望保留核心方向并降低当前操作负担 | 可做删减、重组或必要重构，以实际问题为准 |
| “这个没必要吧” | 用户在质疑该项价值 | 先判断必要性；可以移除、隐藏、自动化或解释保留理由 |
| “这两个是不是重复” | 关注重复入口或重复信息 | 核对职责和数据来源后决定合并、区分或保留 |
| “根据实际情况调整” | 不希望继续使用静态假设 | 结合当前门店、日期、来源和功能成本选择联动方式 |
| “继续优化这个板块” | 延续当前目标 | 通常聚焦当前板块，但必要的关联改动不被禁止 |
| “你自己做”“你看还有哪些” | 技术细节交给 Codex 判断 | 在当前业务目标内自主补齐；重大业务边界仍需尊重 |
| “完成了吗”“还有哪些” | 想了解真实状态和剩余缺口 | 可以复查必要证据，但避免用无关扫描代替直接回答 |
| “不能直接……吗” | 希望寻找更短路径 | 比较直接路径的收益、风险和实现成本后选择 |

疑问句只作为上下文信号，由 Codex 结合当前请求、页面对象、既有权限和实际风险正常判断，不额外设置统一的授权或确认规则。

## 设计取舍提示

遇到冲突时，可参考以下方向，但不作为固定优先级：

| 冲突 | 常见偏好 | 仍需考虑 |
|---|---|---|
| 简洁与真实 | 用更清楚的方式保留真实缺口 | 数据口径和阻断风险 |
| 自动化与控制 | 自动处理重复动作，提供必要接管方式 | 频率、失败成本和权限 |
| 功能完整与易用 | 突出高频路径，按需展示高级能力 | 专业用户和复杂场景 |
| 信息丰富与可读 | 保留能影响判断的事实 | 对比、解释和追溯需求 |
| 快速交付与稳定 | 优先最小可用结果 | 改动风险和必要验证 |
| 局部修改与重构 | 通常保护已验证部分 | 技术债是否已阻碍当前结果 |

## 三源定时发送的当前案例

在 2026 年 7 月这次三源发送页面反馈中，用户希望后台能配置发送内容和固定时间，并认为“每隔多少分钟、循环开始、循环结束”过于复杂。

对当前固定时间计划，可优先考虑：

- 发送内容或来源；
- 固定发送时间；
- 必要的生效范围；
- 目标通知群；
- 启用或暂停；
- 与所选计划一致的企业微信消息预览。

这是当前案例，不是永久禁止间隔循环。如果未来业务明确需要高频轮询、循环窗口或多种调度模式，可以按新的需求设计。

## 可选的理解提示

当页面需求复杂或表达存在多种合理解释时，可以在内部快速确认：

1. 用户当前最想得到的业务结果是什么？
2. 哪些内容已被明确要求保留或排除？
3. 什么证据最能证明这次结果真实可用？

这是思考提示，不是必须输出的表格，也不要求用户逐项回答。

## 防止过度拟合

不要从这份参考推导出以下僵硬规则：

- 每页只能有一个操作；
- 所有低频功能都必须放进“更多功能”；
- 所有手动动作都必须同步直返；
- 为所有疑问句预设统一处理方式；
- 任何页面都不能重构或新增导航；
- 技术测试不重要或可以省略；
- 所有缺失字段都必须隐藏；
- 三源发送永远不能支持间隔循环；
- 固定卡片数、字段数、步骤数、文字长度或验收顺序；
- 过去一次页面反馈自动适用于以后所有模块。

目标是帮助 Codex 更准确地理解用户，而不是替代 Codex 的推理。
