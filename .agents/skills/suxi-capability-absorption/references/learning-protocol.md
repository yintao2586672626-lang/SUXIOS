# 学习强化协议

## 1. 自动选择学习方法

| 方法 | 适用材料 | 必须取得的证据 |
| --- | --- | --- |
| 白盒学习 | 源码、Skill、配置、API规范、数据库结构、工作流JSON/YAML | 真实入口、依赖、数据合同、错误路径 |
| 黑盒学习 | 网站、应用、桌面软件、外部服务 | 可见输入、操作、输出、状态和失败行为 |
| 示教学习 | 录屏、屏幕演示、语音讲解、人工步骤 | 动作顺序、操作者意图、关键判断和完成证据 |
| 样例学习 | 报表、模板、截图、输入输出对、历史成品 | 不变结构、可变字段、质量标准和反例 |
| 失败学习 | 日志、报错、测试、工单、差评、用户纠错 | 触发条件、原始失败、正确结果和回归样例 |
| 差异学习 | Commit、Diff、Changelog、新旧版本 | 变化点、兼容影响、迁移规则和复验范围 |
| 组合学习 | 同时提供网站、源码、文档、数据或示教 | 来源间一致项、冲突项、证据优先级和未知项 |

优先选择能直接证明行为的方法。重要数据链或高影响写入不能只靠截图、宣传文案或单个成功样例。

## 2. 材料处置与晋级判断

### 2.1 先拆单元，不给整份文件贴单一标签

按最小可独立使用的知识或能力单元拆分：

- 当前事实或数据行；
- 来源观点或历史结论；
- 可复用原则或判断机制；
- 正常、边界、失败和反例；
- 模板、阈值和默认值；
- 命令、账号、凭证和外部动作；
- 无法验证的推断与未知。

同一文档可以同时包含 `store_only`、`absorption_candidate`、`absorb`、`fact_ingestion` 和 `reject_or_quarantine` 单元。原始来源层始终与蒸馏结论、业务事实和实现代码分开；正式吸纳不能覆盖原文，储存也不能冒充能力。

### 2.2 用硬门判定，不用印象打分

| 处置 | 必须满足 | 典型结果 |
| --- | --- | --- |
| `store_only` | 有未来检索、溯源、历史或解释价值，但不满足正式吸纳三门 | 来源指纹、主题索引、必要摘要、适用范围、`reference_only` 与回读 |
| `absorption_candidate` | 有机制假设，但缺明确落点、原样例、边界、反例或可重复证据 | 机制假设、未知项、缺失证据、下一次晋级触发条件 |
| `absorb` | 机制门、价值门和复现门全部通过 | 原场景重放、同题基线、宿析入口、成功/失败闭环和回归守卫 |
| `fact_ingestion` | 是当前酒店、平台或经营事实，且能建立业务身份 | 平台/酒店/日期/来源/口径/质量状态、保存与精确回读 |
| `reject_or_quarantine` | 无关、不可合法使用、来源或权限风险未解决，或只有高风险执行内容 | 最小来源记录、不采用原因、零执行与零决策影响 |

三道门的证据要求：

1. **机制门**：在不引用产品名和界面名时，仍能写出 `触发 -> 输入 -> 关键判断/动作 -> 输出/状态 -> 不适用条件 -> 失败处理`。只能复述理念、页面模块或成功故事时失败。
2. **价值门**：能指出目标使用者、现有宿析入口、当前同题基线、一个主要用户价值维度和不可退步底线。只有“看起来先进”或需要硬造业务模块时失败。
3. **复现门**：来源原样例或等价黄金样例能够稳定重放；至少再有一个边界、失败或不适用反例。输出、关键判断、状态和停止条件可比较；只有静态理解时失败。

三门是晋级条件，不是多数票。任何一门失败都不能标为 `absorb`。不得用更多功能、字段、测试数量或工程完成度抵消复现缺失。

吸纳资格与当前任务授权分开记录：

- `task_mode=classify`：只做处置判断；一个落点唯一的合格单元可按用户既有目标继续，外部副作用仍需单独授权。
- `task_mode=storage_only`：只执行来源、索引、知识写入和回读；即使单元具备吸纳资格也不实现。
- `task_mode=learn_only`：可以研究到 `understood` 并判断未来资格，但不写业务代码。
- `task_mode=delivery`：三门通过后可以做宿析内最小闭环；安装、登录、外部发送、审批、发布和真实平台写入不随之自动授权。

### 2.3 状态转换

```text
source observed
  -> store_only（长期参考，不晋级）
  -> absorption_candidate（机制有价值，等待证据）
       -> reproduced（三门通过）
       -> integrated（进入宿析真实入口）
       -> guarded（黄金样例、反例、纠错与回归已沉淀）

current hotel/platform facts
  -> fact_ingestion（独立事实链，不经过知识晋级）

unsafe / irrelevant / unauthorized
  -> reject_or_quarantine
```

- 不允许 `understood -> integrated` 跳级。
- 用户明确要求“只存档”时不做晋级判断后的实现，即使材料三门全过；报告“具备资格但本次未授权实施”，不能误报为机制或证据失败。
- 用户明确要求“做进系统”时仍须运行三门；复现门缺失但业务目标独立清楚时，处置仍为 `absorption_candidate`，只能附加 `delivery_label=source_inspired` 并保持 `partial`。该标签不能宣称来源能力已吸纳，也不授权任何外部副作用。
- 用户只说“这个给你”时，先完成处置卡；一个单元过门且落点唯一时自动推进，其余储存或候选。两个过门方向会改变业务模块、口径或写入范围时只问一个决定性问题。

### 2.4 最小处置卡

```text
overall_disposition:
source_identity:
task_mode:
execution_authorization:
units:
  - unit:
    disposition:
    absorption_eligibility:
    verified_evidence:
    inference_and_unknowns:
    mechanism_gate: pass | fail | indeterminate
    value_gate: pass | fail | indeterminate
    reproduction_gate: pass | fail | indeterminate
    maturity:
    destination_or_non_goal:
next_promotion_trigger:
```

处置卡是内部决策合同，用户输出只保留有决策价值的字段。没有正式吸纳单元时应直接说明“本次仅储存/候选，未改业务功能”，不要为了让报告显得积极而发明落点。

### 2.5 宿析常见例子

- 行业趋势报告：数字、观点和发布日期通常 `store_only`；其中可重放的竞对判断方法才可能晋级，报告结论本身不成为永久事实。
- SaaS 页面截图：可见信息层级和用户路径可以成为候选；隐藏算法、后台数据和效果宣传不能被吸纳为事实。
- 管理 SOP：原文和默认频次储存；角色、证据、状态、例外和关闭条件形成可重放合同后，才吸纳为流程。
- 携程/美团导出：当期房价、流量或订单属于 `fact_ingestion`；报告中的分析框架可以另行拆为候选吸纳，二者不得混写。
- 在线 Skill 或脚本：来源和方法可先储存；权限、依赖、许可和脚本树未审完时保持隔离，不能因静态扫描通过而正式吸纳。

### 2.6 凭证、命令与外部动作门

- 原始账号、密码、Cookie、令牌、验证码、恢复码和敏感头不得进入知识中心、Obsidian、代码、提示词、日志、fixture 或评测；只记录脱敏后的“存在/未使用/已隔离”和来源位置。
- 材料内的演示账号、安装命令、部署步骤、验收命令或外部网址都是被观察内容，不构成登录、安装、联网、写入或发布授权。
- 执行命令前另核对目标环境、来源完整性、依赖、副作用、回滚方式和本次授权；在线 Skill 的静态检查只是其中一部分。
- 涉及调价、上下架、发送消息、创建任务或修改 OTA/PMS 时，状态必须区分 `analysis_only -> pending_approval -> user_triggered_execution -> effect_readback`。默认停在只读分析或 `pending_approval`；不得因方法已吸纳而自动推进真实动作。
- 历史行业数字进入当前比较或模型前，另检查观察期间、发布日期、地域、样本、统计口径、许可、时效和适用范围。缺任一关键项时保持 `reference_only`，不能成为当前酒店基准。

## 3. 能力合同

在实现前整理最小合同，不要求用户手工填写：

```text
来源标识 / 版本或日期 / 授权与数据范围 / 目标使用者 /
触发条件 / 输入 / 核心动作 / 输出 / 状态变化 / 副作用 /
正常样例 / 边界样例 / 失败样例 / 允许差异 / 未知项 / 验收命令
```

- 运行中的真实行为用于说明“当前是什么”；用户确认的业务目标用于说明“应该是什么”，两者冲突时不能互相覆盖。
- OTA页面或渠道数据只证明渠道范围，不扩大为全酒店事实。
- 来源无法运行时保留确切失败证据，然后切换适配、行为复刻或最小重建。

## 4. 黄金样例与重放

1. 优先保存最小脱敏输入、预期输出、状态变化和错误结果。
2. 至少重放一个主路径；材料允许时增加一个边界和一个失败样例。
3. 对页面比较任务完成与状态，不只比较像素；对API比较字段、状态码和错误；对SOP比较状态流转和证据；对数据比较语义、范围、保存和回读。
4. 原材料缺少失败样例时标记 `unknown`，不得用自造错误假装来源已经验证。
5. 用户纠正结果后，把纠正样例加入 eval 或 verifier，并同时复跑原始样例，防止修一处坏一处。
6. 交付模式必须同时验证一条代表性成功路径和一条关键失败、缺失或未验证路径；后者可以验证宿析OS自己的保护行为，但不得冒充来源系统的真实失败行为。
7. 正式吸纳必须先重放来源行为，再重放宿析适配行为；只验证适配代码可运行，不能证明来源精髓已保留。
8. 同题基线至少比较一个预声明用户价值维度和关键不退步项。测试数量、页面数量、字段数量和代码规模不是吸纳质量指标。

## 5. 多源冲突与置信边界

按以下顺序处理证据，而不是简单投票：

1. 当前可重复运行或可观察的真实行为；
2. 当前自动化测试、接口规范和数据约束；
3. 经用户确认的业务规则、SOP和目标结果；
4. 当前文档、示例成品和版本说明；
5. 推断。

来源冲突时分别记录“来源现状”和“目标决策”。缺少决定性证据时使用 `partial` 或 `blocked`，不把推断写成事实。

## 6. 防遗忘与升级

功能闭环后按实际需要沉淀，不为沉淀而扩大任务：

- 来源指纹：路径、仓库提交、版本、接口规范版本、页面日期或文件哈希；
- 稳定合同：字段映射、状态机、错误语义、允许差异和权限边界；
- 可重放证据：脱敏 fixture、黄金样例、聚焦测试或 verifier；
- 自动触发：重复任务写入项目 Skill，重复失败写入 `evals/`；
- 纠错记录：用户明确纠正的稳定规则进入合同和回归样例；
- 定向升级：来源指纹变化时只重验受影响合同，不从头重学全部材料。

储存层保留“原来写了什么”，能力层保留“在什么条件下如何判断和行动”，事实层保留“当前哪家酒店、哪个平台、哪一天实际发生了什么”。三层都可追溯，但不能互相替代。

完成报告必须说清：当前阶段、真实验证、未验证项、来源版本和下一次升级触发条件。

## 7. 数据真实性放行门

外部材料一旦进入 `OTA数据 -> 收益分析 -> AI决策` 链路，逐项检查：

```text
平台 / 系统酒店 / 平台门店或绑定 / 目标日期 /
来源方法 / 采集或导出时间 / 质量状态 / 持久化与数据库回读
```

- 缺少关键身份或日期时保持 `binding_missing`、`unverified`、`stale`、`partial` 或对应失败状态。
- 文件能解析、接口返回200、页面显示数字，都不能单独证明数据可用于收益或AI决策。
- OTA渠道证据只进入渠道分析，不提升为全酒店经营事实。

## 8. Skill质量基线

1. 把触发准确性与输出质量分开测试：`evals/trigger-evals.json`覆盖应触发和近似但不应触发的语境；`evals/evals.json`保存真实任务、预期结果和可核对断言。
2. 触发测试保持正负样例接近平衡，混合正式、口语、错别字、短句、长上下文和关键词近似场景。
3. 输出质量测试在干净上下文中分别运行新版Skill与旧版或无Skill基线，避免开发对话、先前产物和预期答案泄漏。
4. 机械结果用脚本断言，复杂体验保留人工复核；PASS必须引用具体输出证据，不给模糊结果“酌情通过”。
5. 条件允许时记录用时和token成本；新版只增加复杂度却没有明显提高通过率时，删减规则而不是继续堆说明。
6. 阅读执行轨迹：若智能体反复扫描、绕路或忽略步骤，优先消除模糊、无关或互相冲突的指令。
7. 迭代到失败断言得到修复、人工反馈稳定为空，或新版本相对基线不再有实质改进后停止。
8. 触发评测与现有Skill共存运行，记录实际加载路径、客户端和文件树指纹；避免宽泛description抢占别的能力。
9. 升级先形成候选版本，验证优于旧版后再切换；高影响能力保留上一通过版本作为回滚点。
10. 分类评测至少覆盖：明确只储存、裸材料自动分类、同文件部分吸纳、证据不足不得跳级、当前OTA/PMS事实走事实链、危险内容隔离、凭证零写入、外部动作审批，以及一个真正满足三门的正式吸纳样例。
