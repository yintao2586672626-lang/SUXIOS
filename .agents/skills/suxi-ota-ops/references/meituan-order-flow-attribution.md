# 美团订单流失/流入归因口径

## 结论

订单流失与订单流入是平台授权数据给出的 OTA 渠道内行为归因，比公开库存变化更接近订单事实，但仍不等于客户选择原因，也不等于全酒店流失或流入。

- `loss`：平台把同时浏览过本店和其他酒店、最终在其他酒店下单的订单归到流失方向。
- `inflow`：平台把同时浏览过其他酒店和本店、最终在本店下单的订单归到流入方向。
- “哪些客人”在宿析OS中应表达为“订单流向哪些竞对、从哪些竞对流入”，默认只展示聚合酒店和房型，不展示可识别客人身份。

订单流向只回答“平台归因到哪里”，不能单独回答“为什么流失”。价格、房型权益、排名、评分、流量、库存等只能作为后续独立核对证据。

## 宿析OS现有底座

宿析OS已有美团订单流向的可用闭环，后续统一对照页和行动建议应复用，不另造采集链路：

- `app/service/MeituanOrderFlowService.php`
  - 使用美团订单流向端点。
  - 通过 `lossType=0/1` 分别请求 `loss` 与 `inflow`。

- `app/controller/concern/OnlineDataManualFetchConcern.php`
  - 两个方向分别执行并保留各自成功/失败状态。
  - 两边成功才返回 `complete`；只有一边成功返回 `partial`。
  - 自动保存后必须通过数据库回读，否则返回失败，不能提示已完成。
- `resources/frontend/templates/fragments/26-page-meituan-ebooking.html`
  - 已有同页的流失/流入摘要和酒店明细入口。
  - 未返回的一侧显示 `-`，不以 `0` 代替。
- `tests/automation/meituan_order_flow_closure.test.mjs`
  - 已守卫门店、期间和登录会话范围。
  - 已守卫成功提示必须晚于匹配范围的数据库回读。
  - 平台明确返回的真实 `0` 会被保留。

## 事实字段与范围

每组结果至少绑定：

| 类别 | 必要字段 |
| --- | --- |
| 身份范围 | `platform`、`system_hotel_id`、平台 `poi_id`/酒店 ID |
| 时间范围 | `period_start`、`period_end`、业务期间、`captured_at` |
| 方向 | `loss` 或 `inflow` |
| 汇总事实 | `order_count`、`room_nights`、`amount`，三种单位分别展示 |
| 对手明细 | 流向/来源酒店 ID 与名称、订单数、占比、金额 |
| 产品明细 | 房型名称与对应数量；无法确认单位时保留原字段并标记未验证 |
| 证据状态 | 来源方法、方向状态、持久化状态、回读状态、失败原因、新鲜度 |

订单数、间夜和金额不能相互替代。允许分别计算：

```text
净订单流 = 流入订单数 - 流失订单数
净间夜流 = 流入间夜 - 流失间夜
净金额流 = 流入金额 - 流失金额
```

这些结果只能命名为“美团渠道净订单流/净间夜流/净金额流”，不能命名为全酒店净增订单、净增间夜或净营收。

## 状态规则

| 状态 | 含义 |
| --- | --- |
| `complete` | `loss` 与 `inflow` 均成功规范化、保存并按同一门店和期间回读；平台明确返回的合法 `0` 也属于完整结果 |
| `partial` | 只有一个方向成功并完成保存回读，另一方向失败或缺失 |
| `no_saved_data` | 当前门店和期间没有已保存结果，尚不能判断为零 |
| `collection_failed` | 两个方向均未获得可规范化结果 |
| `login_expired` | 授权会话失效，需要用户重新登录平台 |
| `binding_missing` | 系统酒店与平台酒店/POI 未完成绑定 |
| `readback_failed` | 响应已取得但保存后无法按同一范围回读 |
| `stale` | 已保存结果超过业务允许的新鲜度 |
| `unverified` | 来源、门店、期间、字段语义或归因规则尚未核实 |

缺数据、接口失败和真实 `0` 是三种不同事实。只有平台成功响应中明确存在数值 `0`，且范围和回读均通过，才允许显示 `0`。

## 统一对照页允许输出

- 流失与流入的订单数、间夜、金额并列对照。
- 三种单位各自的净流变化，不合并成单一“经营得分”。
- 流失去向酒店 Top N、流入来源酒店 Top N。
- 流失/流入集中的房型、酒店、期间及其占比。
- 与上一个可比期间的变化，但必须回显两个期间和采集时间。
- 数据质量、失败方向、保存回读和新鲜度。

## 行动建议

建议必须沿用：

```text
订单流向事实 → 待验证原因假设 → 人工可执行动作 → 责任人/期限 → 次周期复盘
```

可生成的动作示例：

1. 流失集中到某酒店：建立价格、房型权益、评分、排名、库存的独立对照任务，未核对前不写原因。
2. 流失集中在某房型：核对该房型的价差、早餐/取消政策、图片与名称表达，并记录复盘指标。
3. 流入集中来自某酒店：识别本店可能的优势并设置“保持”动作，仍需其他证据验证。
4. 净订单流连续恶化：生成带责任人、截止时间和下个 7 日复盘节点的运营工单。

AI 输出必须同时包含事实依据、缺口、置信度和建议由谁复核。订单流向本身不允许直接生成“因为价格高”“因为评分低”等确定性结论。

## 禁止用途

- 不得把一个方向成功写成完整双向结果。
- 不得把没有结果、请求失败、登录失效或回读失败显示成 `0`。
- 不得把流向关系写成客户选择的确定原因。
- 不得把美团渠道归因扩大为全酒店流失、全酒店营收或全渠道客户迁移。
- 不得用竞对公开库存变化替代平台授权订单流向。
- 不得展示客人姓名、手机号、证件号、订单号等直接身份信息。
- 不得把订单数、间夜和金额混成同一单位或用一个单位推导另一个单位。

## 黄金样例

1. `loss` 与 `inflow` 都成功、保存且同范围回读：状态为 `complete`，分别展示订单数、间夜和金额。
2. `loss` 成功而 `inflow` 失败：状态为 `partial`；流入一侧显示 `-` 和失败原因，不显示 `0`。
3. 两个方向都成功且汇总字段明确为 `0`：状态仍可为 `complete`，显示真实 `0` 并保留来源和回读证据。
4. 70% 的流失订单归向酒店 A：只能说“平台归因的流失集中到酒店 A”，下一步核对价格、产品和流量；不得直接说“客户因价格选择 A”。
5. 美团近 7 天净订单流为 `-12`：只能写“美团渠道净订单流 -12”，不得写“全酒店少了 12 张订单”。
6. 页面只显示流向酒店和房型聚合：不得包装成“可查看具体哪些客人”，也不得尝试补采客人身份。
