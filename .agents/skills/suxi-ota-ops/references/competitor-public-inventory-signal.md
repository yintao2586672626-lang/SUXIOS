# 竞对公开库存变化信号口径

## 结论

竞对公开页库存快照是真实可观察的 OTA 页面证据，但不是酒店物理总库存、后台订单或真实渠道销量。

两个快照之间的库存净下降只能记录为派生信号：

```text
公开库存净下降 = max(0, 基线可见库存 - 最新可见库存)
公开库存净增加 = max(0, 最新可见库存 - 基线可见库存)
```

不得把 `公开库存净下降` 直接命名或写入为 `竞对销量`、`竞对订单数`、`竞对真实卖房量`、`竞对出租率` 或 `竞对营收`。

## 为什么不能识别真实销量

页面可见库存由多种状态共同决定：

```text
页面可见库存
= 物理库存
+ 渠道分配
+ 房型和价格计划
+ 最少连住、关房、停售等售卖限制
+ OTA 展示上限和展示规则
+ PMS/渠道管理器同步状态
```

因此一次库存下降可能来自新订单，也可能来自关房、停售、渠道调拨、房型调整或采集误差；库存增加可能来自取消、补房或库存释放。仅凭两个快照无法识别这些原因。

基线与最新快照的比较只能得到净变化。例如库存经历 `10 → 5 → 9`，最终净下降是 `1`，不能据此证明期间只卖出 `1` 间，也无法恢复期间的全部预订和取消。

## 单位边界

监控范围按入住日期展开。若把多个入住日期的下降量相加，结果更接近推算间夜变化，不一定是房间数或订单数。

一张 `1 间 × 3 晚` 的订单可能让三个入住日期分别下降 `1`，合计为 `3` 个间夜变化，但真实订单仍只有 `1` 张。没有订单级凭据时不得写成 `卖出 3 间` 或 `3 张订单`。

## 宿析OS允许用途

- `竞对公开库存净下降（推算）`
- `竞对公开库存净增加`
- `竞对售罄扩散率`
- `价格—可售状态联动`
- `竞争圈需求压力信号`
- 竞对房态异常提醒和人工核对任务

只有多家竞对在相同目标入住日期出现同向变化，并得到价格、流量、搜索热度或排名等独立证据支持时，才允许输出“需求可能升温”等带置信度的 OTA 渠道判断。

## 禁止用途

- 不得进入真实订单、真实间夜、出租率、ADR、RevPAR 或营收核算。
- 不得把携程公开页变化扩大为全酒店经营事实。
- 不得用当前公开价乘净下降量后称为真实流水。
- 不得在缺基线、采集过期、房型不可比、售罄映射未知或平台展示受限时补零。
- 不得让 AI 把相关性写成订单成交原因或确定性市场结论。

## 推荐状态

| 状态 | 含义 |
| --- | --- |
| `available` | 原始公开库存快照的门店、平台、入住日期、采集时间、来源和回读均已验证 |
| `derived` | 由两个可比快照计算的净变化，必须指向输入快照 |
| `partial` | 只有部分日期、房型或竞对可比 |
| `stale` | 最新快照超过业务允许的新鲜度 |
| `insufficient_evidence` | 缺基线、缺最新值、房型不可比或展示上限未知 |
| `unverified` | 来源存在，但平台门店、日期或字段语义尚未核实 |

`available` 只证明快照可用，不会把派生变化升级成真实销量。

## 黄金样例

1. 基线 `10`、最新 `7`：输出“公开库存净下降 3（推算）”，不得输出“竞对卖了 3 间”。
2. 基线 `10`、日内 `5`、最新 `9`：输出“相对基线净下降 1”，并说明无法还原日内预订和取消。
3. 基线 `10`、最新 `12`：输出“公开库存净增加 2”，原因保持未知，不直接写“补房 2 间”。
4. 缺少基线：输出 `insufficient_evidence`，不得用 `0` 代替。
5. 一张连住三晚订单造成三个入住日各下降 `1`：只允许表述为“推算间夜变化合计 3”，不得解释为三张订单。
