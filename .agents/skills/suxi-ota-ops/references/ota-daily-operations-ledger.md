## 可复用的记录方法

1. 晨班记录前一业务日数据；城市排名按采集当日记录，同时保留 `data_date` 与 `collected_at`，避免把业务日和采集日混成一个日期。
2. 每个业务日一条记录，携程与美团分平台保存；月份只是查看分区，不应成为数据主键。
3. 原始事实、平台分值、系统派生指标、人工备注必须分开：
   - 原始事实：曝光、浏览、订单、间夜、销售额、均价、排名。
   - 平台分值：携程服务质量分等，只保存平台展示值，不反推私有公式。
   - 派生指标：曝光转化、下单转化，由系统统一计算。
   - 人工备注：运营假设、已执行动作及异常说明，不作为已验证事实。
4. 本店与商圈/同行平均使用相同口径并排展示，先定位漏斗阶段，再提出动作。
5. 每次保存后必须回读；日报或截图只能引用已回读的数据版本。

## 公共身份与证据字段

每条日台账至少绑定：

| 字段 | 规则 |
| --- | --- |
| `system_hotel_id` | 宿析OS门店身份，必填 |
| `platform` | 仅允许当前记录对应的平台，如 `ctrip`、`meituan` |
| `platform_hotel_id` | 平台门店身份；缺失时数据保持未核验 |
| `data_date` | 指标所属业务日 |
| `collected_at` | 实际采集或导入时间 |
| `source_method` | `profile_capture`、`manual_entry`、`file_import` 等 |
| `source_ref` | 脱敏后的导出文件指纹、采集任务或证据引用 |
| `operator_id` | 人工录入或复核人 |
| `quality_status` | `verified`、`partial`、`unverified`、`blocked`、`invalid` |
| `saved_at` / `readback_status` | 保存时间及回读结果 |

缺少门店、平台、日期、来源或回读证据时，不得把记录升级为 `verified`。

## 携程台账口径

### 基础事实

- 日期、星期、城市排名、APP 访客数、服务质量分。
- 携程、同程、去哪儿的订单数与间夜数；订单数和间夜数不得混用。
- 云梯、金字塔、付费流量及备注只在有明确来源时记录。

### 携程漏斗

本店与商圈分别记录：

- 列表曝光量。
- 详情页访问人数。
- 曝光转化率 = 详情页访问人数 ÷ 列表曝光量。
- 订单页访问人数。
- 下单转化率 = 订单页访问人数 ÷ 详情页访问人数。

原表对应公式关系为：

- `P=N/L`、`Q=O/M`：本店/商圈曝光转化。
- `T=R/N`、`U=S/O`：本店/商圈下单转化。

### 去哪儿漏斗

本店与商圈分别记录列表曝光、详情页访问、订单页访问及两级转化：

- `Z=X/V`、`AA=Y/W`：本店/商圈曝光转化。
- `AD=AB/X`、`AE=AC/Y`：本店/商圈下单转化。

## 美团台账口径

本店与同行平均并排记录：

- 曝光 PV、浏览 UV、支付订单。
- 浏览转化率 = 浏览 UV ÷ 曝光 PV。
- 支付转化率 = 支付订单 ÷ 浏览 UV。
- 销售间夜、入住间夜、平均房价。
- 商圈、品类、城市等平台排名及差评数量。
- 备注中的判断和动作必须标注为人工假设或执行记录。

原表对应公式关系为：

- `J=F/D`、`K=G/E`：本店/同行浏览转化。
- `L=H/F`、`M=I/G`：本店/同行支付转化。

所有除法在分母为空、为零或质量不合格时返回“不可计算”，不得返回 `0`、旧值或默认值。

## 从数据到动作的晨报闭环

标准链路：

`昨日 OTA 事实 → 本店与商圈/同行对比 → 漏斗瓶颈 → 今日动作 → 次日与 7 日复盘`

推荐晨报顺序：

1. 先显示来源、门店、平台、业务日、采集时间、保存回读和质量状态。
2. 展示昨日订单/间夜、曝光、浏览、订单页或支付等原始事实。
3. 同时看本店对商圈/同行差距及近 7 日自身基线，不用单日波动直接定性。
4. 只定位一个首要瓶颈：
   - 曝光不足：优先检查排名、可售、内容覆盖和付费流量。
   - 详情转化偏低：优先检查首图、标题、卖点、展示价和房型表达。
   - 下单/支付转化偏低：优先检查价格竞争力、取消政策、库存、套餐和信任要素。
5. 生成一项可执行动作，绑定负责人、截止时间、完成证据、复盘指标、复盘时间和停止条件。
6. 次日检查动作是否执行，7 日检查是否改善；没有执行证据时不得宣称动作有效。

以上诊断项是排查顺序，不是因果结论。因果结论必须有执行前后证据和复盘结果。

## 已观察到的反例与质量守卫

来源表中观察到以下风险，因此不能直接把历史结果当作真实经营结论：

- 公式与粘贴值混用，存在 `#REF!`、`#DIV/0!`、`#VALUE!`。
- 个别公式引用发生错位，复制公式后未保持本店/商圈分子分母对应。
- 星期公式曾显示 `AAAA`，说明格式或区域设置不稳定。
- 名为 2026 的台账中存在 2025 年日期，月份与年份身份不可靠。
- 缺少系统门店、平台门店、来源方式、采集时间、操作人和保存回读证据。

系统落地时必须：

- 用 `data_date` 计算星期，不接受手工星期作为日期证据。
- 原始值与派生值分开保存，派生指标集中计算，不导入 Excel 公式结果作为权威值。
- 导入时逐行校验日期、平台、门店、分母和单位；错误行进入隔离结果并显示原因。
- 缺数据保持 `unknown` / `unverified` / `blocked`，不使用 0、空数组、旧记录或默认值掩盖。
- OTA 数据只支持对应渠道判断；没有 PMS/全渠道事实时，不输出全酒店出租率、ADR、RevPAR、利润或投资结论。

## 宿析OS最小落地合同

第一阶段只做一个可验收闭环：

1. 携程和美团日台账支持人工录入或文件导入。
2. 保存前完成身份、日期、来源和数值校验；保存后可回读。
3. 系统按固定口径计算转化率并显示不可计算原因。
4. 生成一张“昨日事实—差距—首要瓶颈—今日动作”卡片，同时展示证据、缺口与置信度。
5. 动作可记录负责人、截止时间、完成证据和次日/7 日复盘结果。
6. 支持生成可追溯晨报或截图，但不自动写回 OTA 价格、库存或活动。

验收停止条件是：用户能够找到记录入口、录入/导入、保存、回读、看到真实质量状态、得到一项有证据边界的动作并完成复盘。不要用复制 Excel 页面代替这个经营闭环。
