## 目标

采集不是为了囤积数字，而是持续回答三类问题：

1. **发生了什么**：同一门店、来源和时间口径下的真实事实。
2. **为什么可能发生**：由多期可比证据支持、仍允许被反证的假设。
3. **动作是否有效**：动作前后事实、执行证据和复盘结果是否一致。

统一链路：

```text
最小采集 -> 身份/日期/字段验真 -> 保存与精确回读 ->
建立可比快照 -> 形成待验证假设 -> 记录动作 ->
后续同口径采集 -> 复盘结果 -> 沉淀或否定经验
```

单次采集最多证明一个观察事实，不能直接升级为长期规律或因果结论。

## 从携程采集吸收的经验

1. 携程字段必须闭合为：

   `响应 -> endpoint_id -> source_path -> metric_key -> storage_field -> UI状态 -> verifier`

2. 结构化 JSON 是主证据；DOM 只补平台可见但结构化响应缺失的字段，不能把页面标签或文案当指标。
3. 每个指标保留业务日、采集时间、字段来源、单位、状态和保存回读引用。接口返回 200、数组非空或历史行存在都不等于当前事实可用。
4. 流量、订单、排名、质量、价格和竞争圈属于不同证据模块，不能因为同属携程而互相补值。
5. 携程只能解释携程 OTA 渠道。PMS 的间夜、收入或出租率不能补携程曝光、访客、订单或排名。
6. 当前竞争运营规则对部分异常判断要求至少 4 个可用日期，并用近期可比值形成基线；这是该规则的最低样本门槛，不是所有指标的通用阈值。
7. 异常只用于确定复核方向。例如曝光下降后检查排名、内容、价格和活动；在缺少独立证据时不宣称根因已经证明。

当前主要证据载体包括 `online_daily_data`、`raw_data.facts/field_facts` 和 `ota_ctrip_entity_snapshots`。长期分析必须保留行或快照引用，不能只保留二次汇总值。

## 从订单来了 PMS 采集吸收的经验

1. 先验证系统门店、订单来了平台门店 ID/名称、目标营业日和当前授权会话，再调用最少业务端点。
2. 今日核心、房费明细、区域、单项趋势和远期房态是不同采集意图；普通实时采集不执行无关全量诊断。
3. 采集器先返回结构化事实，再经正式服务保存；临时脚本不直接把页面数字写进业务表。
4. 汇总与房型/房费明细必须对账。只有 `identity_status=matched`、`reconciliation_status=matched`、`quality_status=verified`、`readback_status=readback_verified` 且营业日、酒店一致时，快照才可进入下游。
5. `source_fingerprint` 用于识别同一事实载荷；`captured_at` 用于建立同日时间序列。重复载荷可复用已验证快照，但不能伪装成新变化。
6. 日报、今日实时和未来房态分层保存：
   - 日报回答已结算或已确认的营业日经营事实；
   - 实时快照回答当前经营状态和同日净变化；
   - 未来房态按目标入住日期观察远期变化。
7. 同日两次已验证快照可以计算净已售间夜和房费变化，但它们只是账面净变化。下降可能来自取消、退款、冲账、换房、补录或修订，不能直接命名为流失。
8. 采集间隔过短时变化容易受噪声影响，间隔过长时可比性下降；容量基数变化时重新建立基线，不把房量变化解释为销售节奏。

当前主要证据载体包括 `dingdandao_operating_target_captures`、`dingdandao_room_fee_capture_details` 和 `PmsFactReconciliationService` 的来源差值结果。

## 统一证据包

每个可用于长期复盘的观察至少保留：

| 类别 | 必要内容 |
| --- | --- |
| 身份 | `tenant_id`、`system_hotel_id`、平台/供应商、平台门店 ID 或绑定 |
| 时间 | `business_date`、可选 `target_stay_date`、`captured_at`、时区 |
| 口径 | 模块、`metric_key`、值、单位、事实范围、平台原值或派生值 |
| 来源 | `source_method`、endpoint/页面模块、`source_path`、脱敏 `source_ref` 或指纹 |
| 质量 | 字段状态、整体质量、缺口原因、身份/对账状态 |
| 持久化 | 快照或数据行 ID、保存数量、`readback_status`、回读时间 |
| 可比关系 | 上一条同口径证据引用、比较窗口、不可比原因 |

不得在长期知识中保存 Cookie、token、Profile、Webhook、敏感 HAR 或未脱敏原始响应。

## 三条时间线

### 今日实时

- 同一营业日允许多次采集。
- 只与上一条同门店、同来源、同指标、同口径且已验证的快照比较。
- 显示变化量、采集间隔和可比性；不把多次快照累加成当天总量。

### 昨日复盘

- 使用平台或 PMS 已进入稳定更新窗口、已保存回读的目标营业日事实。
- 先比较近期可比基线、同星期或同经营阶段，再讨论异常。
- 当日实时不能覆盖昨日已结算事实；历史成功也不能代替昨日目标日证据。

### 未来观察

- 以目标入住日期为主键，连续观察同一目标日的流量、预订、房态、价格和提前期变化。
- 携程未来流量是 OTA 渠道需求信号；PMS 未来房态是本店在册预订/房态事实。二者可以互相求证，但不能合并成同一个指标。
- 平台暂未更新或零点窗口不展示时保留 `pending_source_update` / `missing`，不得补 0。

## 从观察到经验

### 1. 观察事实

记录当前数值、相对基线变化、证据引用和缺口。只回答“发生了什么”。

### 2. 待验证假设

把可能原因写成假设，并列出支持证据、冲突证据和下一项最小核对。例如：

- 携程曝光下降，可能与排名、内容覆盖、价格或活动有关；
- PMS 净已售增长放缓，可能与新增预订减少或取消增加有关。

没有独立证据时不得选择一个原因写成事实。

### 3. 动作与完成证据

动作至少绑定负责人、执行时间、对象、预期指标、基线证据、完成证据和复盘时间。没有执行证据时不能评价动作效果。

### 4. 后续复盘

用同门店、同平台/来源、同对象、同指标和同口径的回读事实比较动作前后。保留：

- 改善、无变化、恶化或不可判断；
- 新证据和反例；
- 数据质量、来源合同或经营环境是否发生变化；
- `causality_claimed=false`，除非另有足够的因果设计和证据。

### 5. 经验晋级

知识层使用以下阶段，不把它们冒充现有数据库枚举：

| 阶段 | 含义 |
| --- | --- |
| `observation` | 一次已验证事实 |
| `pattern_candidate` | 多次可比观察出现同向信号，仍可能被反证 |
| `action_reviewed` | 已有执行证据和一次同口径结果复盘 |
| `candidate_sop` | 在明确适用范围内重复有效，等待更多门店或周期复验 |
| `verified_sop` | 适用范围、证据、反例、停止条件和复验周期明确 |
| `invalidated` | 新证据与旧经验冲突，停止继续应用并保留反例 |

每条长期经验至少保存：

`适用门店/平台/模块/时间条件 + 规则或假设 + 支持证据引用 + 反例 + 样本数 + 最近验证时间 + 复验触发条件 + 停止条件`

## 经验不得晋级的情况

- 只有一张截图、一个成功快照或一个历史汇总。
- 门店、平台门店、业务日、目标入住日或采集时间不一致。
- 使用 PMS 补 OTA 缺失，或使用 OTA 推断全酒店出租率、ADR、RevPAR。
- 缺失值被写成 0，或旧数据替代当前目标日。
- 动作没有执行证据，只有指标自然波动。
- 只保留支持结论的样本，忽略失败、反转或不一致证据。
- 平台改版、字段 source path 或指标口径变化后仍沿用旧经验而未复验。

## 当前系统对应能力

- 携程字段证据：`scripts/lib/ctrip_capture_catalog.mjs`。
- 携程多日异常与近期基线：`app/service/CtripCompetitiveOperationsService.php`。
- 订单来了采集、保存和回读：`scripts/run_dingdandao_local_collection.php`、`app/service/DingdandaoOperatingTargetCaptureService.php`。
- PMS 同源时间差值和跨源复核：`app/service/PmsFactReconciliationService.php`。
- 已有 OTA 运营动作的次日同源回读：`app/service/OperationOptimizationReviewService.php`。

这些能力共同证明宿析OS已有“采集—证据—比较—复盘”的基础，但并不表示每个指标、门店和动作都已形成长期经验。每条经验仍须按本合同逐条晋级。
