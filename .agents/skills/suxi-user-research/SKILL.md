# 宿析用户研究与可用性验证

## 目标

把“我觉得好用”转成可核对的用户任务证据，并只支持一个当前产品决定。用户研究用于判断角色、任务、理解与工作流问题；不替代 OTA/PMS 事实、指标定义、数据质量放行或业务审批。

## 证据边界

- 没有真实参与者、观察记录、反馈、问卷或已定义遥测时，状态只能是 `planned`；可以产出方案，不得声称有研究发现。
- AI 角色扮演、虚构 Persona、常识推测、单张截图或自动化测试不是真实用户证据。它们可以生成待验证假设，不得进入“用户已证实”结论。
- 用户或已批准产品目标没有提供时，样本人数、分组配额、会话时长、整体通过率、提前停止数和其他数值门槛一律记为 `pending_decision`，不默认写 5、6、8 人或 5/6、7/8 等“专业数字”。用户明确询问样本或门槛时，可以说明取舍与决定所需信息，但建议值仍标为待批准方案，不是研究事实。
- 未实际查看当前页面、代码、录屏或运行态时，不得写“从当前页面结构看”或声称页面存在某卡片、状态或入口；只能基于用户已给信息列待验证假设，也不预定具体 UI 方案。
- 分开记录 `observed_behavior`、`verbatim_or_self_report`、`system_fact`、`interpretation`、`decision` 和 `unknown`；不把用户说法当作已发生的系统事实。
- 用户研究不得改写可确定的酒店、平台、业务日期、指标口径或来源。发现“用户看不懂 RevPAR”可以促成解释或交互修改，不能促成 RevPAR 公式迎合性变更。
- 只保留研究所需的最小脱敏证据；不把姓名、手机号、住客信息、订单明细、密码、Cookie、Profile 或令牌写入仓库、fixture 或报告。
- 招募、发问卷、联系酒店、录音录屏、外部分享和奖励发放都是外部动作，必须由用户主动触发并处理知情同意。主动触发不等于目标名单、酒店或租户边界、联系方式、参与者同意或录制授权已经齐全；缺少任一执行前提时只准备方案并明确阻塞，不实际发送或录制。

## 模式

- `plan`：定义研究问题、样本边界、任务、中立提示和证据表。没有研究发现。默认只输出状态、一个研究问题、角色范围、1–3个任务、证据字段和唯一下一步；用户未要求时不扩成完整研究手册、招募文案或自拟验收门槛。
- `synthesize`：只综合用户提供或授权读取的真实记录，输出可追溯的观察、解释、冲突与候选改动。
- `retest`：用改版前同角色、同任务、同核心口径复验。条件不可比时标 `not_comparable`，不强行宣称改善。

## 最小研究合同

开始前自主整理，只在缺失项会改变研究对象、数据边界或外部授权时问一个决定性问题：

```text
要支持的一个决定 / 研究问题 /
目标角色与酒店或租户边界 / 实际样本与招募状态 /
当前入口或流程 / 1–3 个真实任务 / 中立提示 /
观察字段 / 隐私与同意 / 验收与停止条件
```

## 方法选择

- 验证“能否找到、理解或完成”：优先真实任务可用性观察。
- 理解工作语境、动机、现有绕行方式：优先半结构访谈，不用诱导问题向用户推销已定方案。
- 估计已定义问题的分布或频率：先明确母体、抽样和题项口径再用问卷；样本不足时不做总体推广。
- 核对大规模行为：只用已定义事件和稳定口径的遥测；没有事件定义、身份或时间窗时保持未知。
- 只有不同来源回答不同问题时才组合方法，不为了显得专业强制访谈、问卷、遥测和竞品研究全部上马。

## 任务与观察

根据当前功能选择最少的真实角色。例如：

- 老板：快速确认什么需要关注、哪个决定需要人工批准。
- 店长：确认某个业务日期的 OTA 数据是否可用，并找到下一个可执行入口。
- 收益或运营人员：核对建议的来源、口径、日期和阻断项，不把候选建议当作事实。
- 前台：按实际流程录入、保存、查看回显并修正一个错误。
- 管理员或培训老师：检查权限、解释口径，并让使用者用自己的话复述关键状态。

每个任务只记录当前决定真正需要的字段：

```text
participant_scope / task_id / task_prompt / completion_status /
time_or_steps_if_relevant / critical_error / backtrack / help_needed /
observed_path / verbatim_or_self_report / evidence_ref / notes
```

## 综合与决定

1. 先按任务和行为归类，再解释；不先写结论再挑选支持证据。
2. 对每个发现分开标记频率、任务影响、证据强度和反例；不用多数票掩盖高损失的少数失败。
3. 用 `observation -> interpretation -> recommendation` 输出，冲突反馈保留为分群、情境差异或未知，不强行合并。
4. 单个用户、小样本或定性研究不得写成“所有用户”、“大多数酒店”或精确比例。
5. 一次只推荐一个最可能改善当前决定的小改动，附不可退步底线和同任务复验标准；其他观察保留为候选。

## 状态与完成证据

- `planned`：可执行的研究问题、参与者边界、任务、中立提示和证据表已完整；必须同时写“尚无研究发现”。
- `observed_partial`：已有部分真实记录，但样本、任务或证据不完整；只报已观察范围。
- `synthesized`：每个关键发现都能回指真实记录，且观察、解释、反例和建议已分开。
- `retested`：改版前后在同角色、同任务和同核心口径下重放，差异可核对。
- `not_comparable`：样本、任务、身份、环境或口径发生实质变化，只报各自结果，不宣称改善或恶化。

研究计划完成不等于研究完成，研究综合完成也不等于产品改动或经营效果已完成。研究任务不自动修改 UI、发送问卷、建立运营任务或执行 OTA/PMS 动作。
