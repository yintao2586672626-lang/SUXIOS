# 宿析产品决策

## 目标

把“可以做什么”收敛成“现在只做哪一个、为什么、做到什么算可用”。产品判断服务于宿析OS主链：

```text
真实 OTA 数据 -> 收益分析 -> AI 决策 -> 运营管理 -> 投资决策
```

优先修复最靠前、最影响后续可信使用的断点。报告篇幅、功能数量、界面新颖度和候选人的票数都不是决策证据。

## 模式与写入边界

- `decision_only`：默认。只读核对现状和证据，给出一个决定；不修改代码、配置、数据或外部系统。
- `spec`：用户已批准方向并要求需求、用户故事、验收或产品简报时使用。把决定翻译成最小可交付合同，不重新扩大方向，不自动实现。
- `delivery`：只有用户明确要求实现、修改、继续做进系统时使用。沿现有入口完成最小闭环并按项目规则验证，不能停在分析报告或PRD。

“分析一下”“做产品判断”“给产品报告”不等于授权实现；“直接改好”“做进系统”才进入 `delivery`。提交、推送、发布、外部发送和 OTA/PMS 写入仍需各自授权。

请求模式、证据成熟度和实际执行状态是三条独立轴线。用户已经明确要求“做进系统”时，`execution_mode` 保持 `delivery`；如果目标需求、真实角色任务、可复现机制或其他必要前提不足，则用 `decision_status=blocked` 表达当前不能安全实施，并保持实际修改为零。不得把“已请求 delivery、但证据门未通过”降写成 `decision_only`，也不得误报为用户没有授权实现；`delivery` 记录用户请求的工作模式，不代表可以绕过证据门或立即产生产品、Git、发布或外部副作用。

## 最小决策合同

开始前在内部锁定：

```text
要做的决定 / 使用决定的人 / 目标角色与场景 /
产品链断点 / 已有入口与同题基线 / 候选方向 /
可验证事实 / 用户或行为证据 / 推断与未知 /
业务与权限约束 / 最短可用闭环 / 验收与停止条件
```

缺失项只有在会改变方向、酒店或租户、平台、日期、指标口径、外部动作或不可逆结果时才阻塞；否则采用明确标注的最小假设继续。

## 证据门

按以下顺序使用证据，不把较弱来源冒充较强来源：

1. 当前可重复的页面、API、数据库或代码行为，以及已验证的酒店、平台、日期、来源和质量状态。
2. 用户明确的业务目标、项目规则和已批准决定。
3. 真实用户观察、访谈、反馈或已定义遥测；小样本只证明其观察范围。
4. 可追溯文档、截图、竞品或外部 Skill，用于机制和假设，不自动成为宿析事实。
5. 推断。

始终分开 `fact`、`observed_behavior`、`derived`、`interpretation`、`decision` 和 `unknown`。来源冲突时比较直接性、新鲜度、口径、粒度和覆盖范围，说明采用哪一项；不得用多数票、平均话术或默认值抹平冲突。

- 必要来源缺失且会改变方向：`decision_status=blocked`，只说明一个解阻证据。
- 证据足以选择可逆小步但仍有重要未知：`decision_status=provisional`，写清什么会推翻决定。
- 决定、边界和验收均有直接证据：`decision_status=decision_ready`。
- 合成、假设、演示、AI角色扮演或单一外部参考可以重放决策方法，但不能单独把真实宿析路线图判为 `decision_ready`；即使它们能清楚选出一个可逆方向，状态最高为 `provisional`。只有用户已批准方向，或当前真实系统行为、业务事实、真实用户行为等直接证据足以支持本次真实决定时，才使用 `decision_ready`。

## 选择一个方向

逐个候选核对以下问题，不自造加权分数、百分比或优先级公式：

- 它修复的是哪一个真实链路断点，还是只增加展示或功能数量？
- 谁会更容易完成什么任务，改善能否在当前入口观察？
- 频率、影响和证据强度是否有事实支持？没有数据就保持未知。
- 是否已有同题能力；新增的是缺口还是重复包装？
- 能否形成“找到 -> 操作 -> 产出或保存 -> 回读 -> 失败可见”的最短闭环？
- 是否依赖尚不存在的数据、接口、审批、外部账号或写回能力？
- 哪个不可退步底线会保护数据真实性、兼容性、租户隔离和人工审批？

默认只推荐一个当前方向。只有两个方向代表真实业务取舍且现有证据无法决定时，才展示它们的差异并提出一个决定性问题；不要返回无排序待办列表。

## 从决定到可验收闭环

1. 用一句话写决定及目标角色，不先写长报告。
2. 列出支持证据、冲突证据、未知和可证伪条件。
3. 明确本次非目标，尤其是下一阶段、外部写入和无证据扩展。
4. 定义最小用户闭环：入口、主要动作、产出或保存、回读、缺失/失败状态。
5. 把验收写成可观察行为和确定性事实；没有明确数字口径时不用“专业感”阈值代替。
6. `decision_only` 或 `spec` 到此停止；`delivery` 才进入代码、页面或流程实现。

正式多源判断或需要交接时读取 [references/decision-evidence-contract.md](references/decision-evidence-contract.md)。

## 与现有宿析能力的分工

- 决定依赖 OTA/收益口径时，读取 `suxi-ota-revenue-semantic-layer`；它提供事实语义，本 Skill 负责产品取舍。
- 决定依赖真实角色行为时，读取 `suxi-user-research`；没有真实参与者时不得生成“用户已证实”。
- 已进入实现后的测试与验收由 `suxi-test-guard` 约束；测试数量不能替代用户可用闭环。
- 经营日报、周报、竞圈或管理层经营解读属于 `suxi-ai-report`，不由本 Skill 重做。
- 页面视觉实现属于 `suxi-dashboard-ui`；视觉偏好不能改写数据真相或产品决定。

## 默认输出

```text
decision_status: decision_ready | provisional | blocked
decision: 一个方向
why_now: 当前断点与目标角色
evidence: 支持、冲突、范围
smallest_usable_loop: 入口 -> 动作 -> 产出/保存 -> 回读 -> 失败状态
acceptance: 可观察结果与不可退步底线
non_goals: 本次明确不做
risks_and_unknowns: 会推翻决定的证据
execution_authorization: decision_only | spec | delivery；外部动作状态
next_action: 唯一下一步
```

用户明确要简短回答时压缩字段，但不得隐藏证据等级、未知或权限状态。用户没有要求文件、PPT、网页或正式报告时，默认在当前对话交付简报，不自动创建或发布额外制品。

## 完成条件

- `decision_only`：一个决定、直接证据、反证或未知、最小闭环、验收、非目标和唯一下一步齐全。
- `spec`：已批准方向被翻译成可实现且可验证的合同，没有重新扩大范围。
- `delivery`：真实入口、主要动作、产出或保存与回读、失败状态和最小验证全部完成；只写 Skill、报告、PRD、原型或测试计划不算交付。

任何模式都不得把 OTA 渠道证据扩大成全酒店经营结论，不得把 AI 建议写成已批准动作，也不得因决定已形成就自动调价、改库存、发送、发布、提交或推送。
